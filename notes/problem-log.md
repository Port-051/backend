# 문제 기록

구현하면서 부딪힌 것과 어떻게 풀었는지를 그때그때 남긴다.
`blog/`가 다듬은 글이라면 여기는 **재료**다. 나중에 글로 옮길 때 이 기록에서 꺼내 쓴다.

## 쓰는 법

- 문제를 만나 고친 **그 자리에서** 추가한다. 커밋 메시지보다 자세히, 블로그 글보다 거칠게.
- 새 항목은 **맨 아래에** 붙인다. 번호는 이어서 매긴다.
- 실제 에러 메시지나 테스트 실패 출력을 그대로 옮긴다. 나중에 검색으로 찾게 된다.
- **버린 선택지를 반드시 적는다.** "왜 그렇게 안 했나"가 나중에 제일 답하기 어려운 질문이다.

각 항목은 아래 틀을 따르되, 없는 칸은 비운다.

```
## N. 한 줄 제목

**증상** 무엇이 어떻게 잘못됐나
**원인** 왜 그랬나
**선택지** 검토한 것들과 각각의 문제
**결정** 고른 것과 이유
**대가** 그래서 포기한 것
**잠금** 다시 그러지 않게 무엇을 걸어뒀나
```

## 1. 계약에 없는 값을 판정에 쓸 뻔했다 — 플레이 가능 시간

**증상** 4.1이 "플레이 가능한 시간이 겹치지 않는다"를 후보 제외 사유로 두는데, 계약(05 2장)이 요청에 담는 것은 `playMinutes`(플레이 길이) 하나뿐이라 겹칠 구간을 만들 수 없었다.

**선택지**
- `[requestedAt, requestedAt + playMinutes]`를 가용 구간으로 보고 교집합 판정 — 신청 시각이 벌어진 사람이 걸러진다. 즉시 매칭에서 말이 안 된다.
- 판정에서 뺀다 — 4.1의 항목 하나가 통째로 죽는다.

**결정** 판정에서 뺐다. 즉시 매칭은 모두 지금 시작하므로 겹칠 구간 자체가 없다. 이 조건은 예약 매칭(별개 기능) 것이다.

**잠금** `CandidateRuleTest.playMinutesIsNotAConditionAtAll` — 플레이 길이가 달라도 후보가 되는지 본다. 나중에 누가 이걸 조건으로 되살리면 깨진다.

## 2. 4.3을 문자 그대로 구현하면 잘못된 파티가 나온다

**증상** 4.3 3단계가 "**기준 요청과** 조건이 맞는 후보를 훑으며"인데, 이대로 하면 4.1을 위반한 파티가 성립한다.

```
기준 철수 = 음성 "가능"
  후보 영희 = "필수"       철수와 호환 ✓ 채택
  후보 민수 = "사용하지 않음"  철수와 호환 ✓ 채택
  → 영희 ↔ 민수는 4.2 표에서 유일하게 막히는 조합인데 아무도 둘을 비교하지 않았다
```

**원인** 4.1의 조건 중 **음성채팅 호환**과 **허용 티어 범위**가 한 다리 건너 성립하지 않는다. 나머지(큐·인원·목적)는 동치라서 기준 하나만 봐도 된다.

**결정** 후보를 **이미 채택된 전원**과 대조한다. 파티가 최대 5명이라 비교가 많아야 10번이다. 명세 문장이 부정확한 것으로 보고 `docs/01-functional-spec-mvp.md` 4.3도 함께 고쳤다(`993c1ee`).

**잠금** `PartyMatcherTest.rejectsCandidatesThatClashWithAnAlreadyAdoptedMember`, `checksTierRangeAgainstEveryMember`

## 3. 다섯 불변식이 못 잡는 위반이 있다 — INV-6

**증상** 같은 사용자의 요청 둘이 한 파티에 들어가면, 검출 질의 다섯 개가 전부 0행을 반환하는데 실제로는 5인 파티를 네 사람이 하고 있다.

| | 왜 못 잡나 |
|---|---|
| INV-1 정원 초과 | 5인 파티에 5행. 정원 안 넘음 |
| INV-2 시간 겹침 | 질의가 `a.party_id < b.party_id` — **같은 파티는 비교 안 함** |
| INV-3 요청 단일 배정 | `request_id`가 서로 다름 |
| INV-4 포지션 중복 | 배정 포지션이 갈리면 통과 |

**결정** `docs/02-technical-spec-supplement.md`에 INV-6을 추가했다(`3d839da`). 강제 수단은 INV-4와 같은 형태의 부분 유니크 인덱스 `UNIQUE (party_id, user_id) WHERE left_at IS NULL`.

**남은 것** 이 스파이크에는 RDB가 없어 제약을 걸 곳이 없다. 대기 명단 쪽 `SET NX`(→ 12번)가 유일한 방어다.

## 4. 그리디 배정이 최선이 아니다 — 포지션

**증상** 포지션을 앞에서부터 채우면 주 포지션을 받는 사람이 줄어든다.

```
P1: 주 MID, 부 SUPPORT
P2: 주 MID, 부 TOP
P3: 주 TOP, 부 JUNGLE

P1에게 MID를 주면 → 뒤의 둘이 밀려 주 포지션 1명
P1이 SUPPORT로 물러나면 → 뒤의 둘이 주 포지션 받아 2명
```

**결정** 완전탐색 + 백트래킹. 최대 5명 × 5자리라 완전한 배정이 120가지뿐이고, 무엇보다 탐색 순서가 코드에 그대로 보여 4.3의 결정성을 눈으로 확인할 수 있다. 헝가리안 알고리즘은 같은 최적해가 여럿일 때 어느 것을 고르는지가 구현 세부에 숨는다.

**잠금** `PositionAssignerTest.prefersTheAssignmentWithMorePrimaries`, `isDeterministic`(20회 반복)

## 5. JDK 직렬화로는 record를 저장할 수 없다

**증상**
```
DefaultSerializer requires a Serializable payload
but received an object of type [com.port051.queuemate.matching.domain.MatchRequest]
```

**원인** 자동 설정된 `RedisTemplate`의 기본 변환기가 JDK 직렬화다. Boot 4에서도 그렇다.

**선택지**
- `Serializable`을 붙인다 — 저장은 되지만 나오는 것이 자바 클래스 이름이 박힌 바이너리다. 부하 스크립트가 못 읽는다.
- `GenericJackson2JsonRedisSerializer` — JSON 안에 `@class`를 심는다. 필드가 14개가 되어 계약 위반이고, 클래스를 옮기면 기존 데이터를 못 읽는다.
- `Jackson2JsonRedisSerializer<MatchRequest>`(타입 고정) — 이건 됐다. 다만 `RedisTemplate`은 **키까지** JDK 직렬화라 `req:10482`가 바이너리 키가 된다. 네 가지 변환기를 다 지정해야 한다.

**결정** `StringRedisTemplate` + 직접 만든 `JsonMapper`. 키·값 모두 UTF-8 문자열이고, `MatchRequestJsonTest`가 이미 검증한 경로를 그대로 쓴다. `JsonMapper`를 주입받지 않은 이유는 이 JSON의 모양이 **계약이지 애플리케이션 설정이 아니라서** 전역 설정에 흔들리면 안 되기 때문이다.

**잠금** `RequestStoreTest.storesTheContractJson`(필드 13개), `neverStoresAJavaOnlyPayload`

## 6. 자바에서 맞은 정렬이 저장소에서 틀렸다 — ZSET 동률

**증상**
```
Expecting actual:  [10L, 9L]
to contain exactly: [9L, 10L]
```
`PartyMatcher`의 결정성 테스트 20개는 전부 통과한 상태였다.

**원인** 4.3의 전순서는 `(신청 시각, 요청 ID)` 두 값인데 Sorted Set의 score는 숫자 하나뿐이다. `requestedAt`을 score에 담고 나면 남은 동률을 Redis가 **멤버 사전순**으로 가르는데 `"10" < "9"`다.

**선택지**
- score에 두 값을 합쳐 담기 — `double`이 정수를 정확히 담는 폭이 53비트인데 epoch millis가 이미 41비트를 쓴다. 남는 12비트로는 요청 ID를 4096개밖에 구분 못 한다. **틀려도 티가 안 난다.**
- 자바에서 다시 정렬 — 전체를 읽으면 맞지만 앞에서 N개만 읽으면 동률이 페이지 경계에 걸린다. 나중에 최적화하면 깨진다.
- List로 바꾸기 — 삽입 순서 ≠ 신청 시각 순, 삭제가 O(N), score 범위 연산이 없어 만료를 못 쓴다.

**결정** 멤버를 19자리로 채운다(`%019d`). 사전순과 숫자 크기 순이 일치한다. 19자리인 것은 `Long.MAX_VALUE`가 19자리이기 때문이고, 짧게 잡으면 큰 ID에서 재발한다.

**대가** `redis-cli`에서 `0000000000000000009`로 보여 덜 읽힌다. `req:`에서 "사람이 읽을 수 있어야 한다"를 이유로 JSON을 골랐던 것과 방향이 반대지만, 여기서는 정확성이 이긴다.

**잠금** `breaksTiesByRequestId`, `ordersByNumericValueNotByText`, `ordersHugeRequestIdsCorrectly`(`Long.MAX_VALUE`), `storesZeroPaddedMembers`(저장 형식 자체)

## 7. Redis의 TTL은 키 단위라 ZSET 멤버 하나만 만료시킬 수 없다

**증상** `EXPIRE mq:... 300`을 걸면 대기 명단 **전체**가 사라진다.

**결정** TTL을 안 쓰고 score 범위로 쓸어낸다.
```
ZRANGEBYSCORE   mq:... -inf {threshold}   만료 대상 조회
ZREMRANGEBYSCORE mq:... -inf {threshold}  한 번에 삭제
```
score가 곧 `requestedAt`이라 **만료 판정이 범위 조회 하나**가 된다. 6번에서 Sorted Set을 고른 값이 여기서 나왔다.

**남은 것** 조회와 삭제가 두 명령이라 두 인스턴스가 같은 요청을 둘 다 지울 수 있다. 지우기는 멱등이라 정합성 문제는 없지만, 만료를 사용자에게 알리는 일이 붙으면 **중복 발송**이 된다. 그때는 "실제로 지운 쪽만 반환"하도록 Lua로 바꿔야 한다.

## 8. 최대 대기시간이 계약 JSON에 없다

**증상** 3.1은 사용자가 고르는 값으로 정의하는데 계약 2장의 필드 13개에 없다. `playMinutes`는 "몇 시간 할 건지"라 다른 값이다.

**결정** 계약은 부하 스크립트가 물고 있어 못 늘리므로 서버 설정값(`queuemate.matching.max-wait: 5m`)으로 뒀다. 계약에 필드가 생기면 요청별 값으로 바꾸면 되고 **판정 지점은 `RequestExpiry` 그대로**다.

## 9. 만료 판정에 앱 시계를 쓰면 안 된다

**원인** `02` 1.5 — "만료·마감·배치 기준 시각은 애플리케이션 시계가 아니라 **데이터베이스 시계**를 사용한다. 인스턴스 간 시계 차이가 판정을 갈라놓으면 안 된다."

**결정** 이 단계에는 DB가 없으므로 그 자리를 Redis가 대신한다(`RedisClock`, `TIME` 명령). 중요한 것은 어느 저장소냐가 아니라 **모든 인스턴스가 같은 시계를 본다**는 것이다. `System.currentTimeMillis()`였다면 경계에 걸린 요청이 어느 인스턴스에서 판정되느냐에 따라 만료가 갈린다.

## 10. Redis에는 롤백이 없다 — 전원 선점

**증상** 계약 3장이 "찾은 전원에게 동시에 `claim`을 건다. 하나라도 이미 걸려 있으면 **전부 취소**"인데, 순진하게 짜면 이렇게 된다.

```
파티 A = [1,2,3]        파티 B = [3,4,5]
#1: 1 잡음, 2 잡음, 3 실패
#2: 5 잡음, 4 잡음, 3 실패
→ 둘 다 실패했는데 1,2,4,5가 잡힌 채로 남는다
```

**선택지**
- `MULTI` — 명령을 묶어 보낼 뿐 실패해도 앞의 것이 안 되돌아간다. 이름만 트랜잭션이다.
- 하나씩 `SET NX` + 실패 시 지우기 — 그 사이에 다른 인스턴스가 끼어든다.

**결정** Lua. **전부 확인 → 전부 설정**을 한 스크립트에 넣는다. Redis가 스크립트를 실행하는 동안 다른 명령을 받지 않으므로 확인 시점의 판단이 설정 시점까지 유효하다. 막히면 `return 0`으로 나가는데, **아직 아무것도 쓰지 않았으니 되돌릴 것도 없다.**

소유자 토큰(UUID)을 함께 둔다. TTL이 먼저 끝나 남이 같은 요청을 잡은 뒤 우리 해제가 도착하면 남의 claim을 지우기 때문이다. 해제도 Lua로 값이 내 토큰일 때만 지운다.

**잠금** `leavesNothingBehindOnFailure`, `overlappingPartiesNeverDeadlockEachOther`(스레드 2개), `onlyOneWinnerWhenEveryoneRacesForTheSameParty`(스레드 16개), `neverReleasesSomeoneElsesClaim`

## 11. 대기 명단이 한 줄이라 섞일 수 없는 요청까지 훑었다

**증상** 솔로큐 30명과 자유랭 100명이 한 줄에 서면 매 틱 `130 × 130`번 비교하는데 대부분이 "큐가 다름"으로 첫 줄에서 죽는다.

**결정** `Partition(queue, targetSize)` 단위로 명단을 나눈다(`mq:SOLO_DUO:2` 등 8개). 4.1이 이 둘을 정확 일치로 요구하므로 조합이 다르면 **어떤 경우에도** 같은 파티가 될 수 없다.

진짜 이유는 성능이 아니다. `02` 1.4의 **파티션 단일 라이터** — 인스턴스마다 다른 조합을 맡기면 겹칠 명단이 없어 claim이 부딪히지 않는다. 지금은 한 인스턴스가 8개를 다 돌지만 나눌 준비는 됐다.

플레이 목적까지 나누면 조합이 네 배로 늘어난다. 값어치가 있는지는 재 보고 정할 일이라 넣지 않았다.

## 12. 사용자당 대기 요청 하나 — 사전 검증은 샌다

**원인** 9.2가 "시간이 겹치는 요청을 중복 생성하지 못하게 한다"고 정하는데, 즉시 매칭은 모두 지금 시작하므로 **조건이 무엇이든 같은 사람의 두 요청은 항상 겹친다.** 그런데 이것을 "조회하고 없으면 넣는다"로 짜면 조회와 삽입 사이에 틈이 생긴다. 더블클릭·재전송이면 두 요청이 거의 동시에 도착해 그 틈이 실제로 벌어진다.

**결정** `SET user:{userId}:waiting {requestId} NX PX {maxWait}`. 확인과 삽입이 한 연산이다. 취소·만료·파티 확정 **세 경로 모두에서** 자리를 비운다. TTL은 그 셋을 다 놓쳤을 때의 안전망이다.

이것이 새면 3번(INV-6)의 위반이 된다. 이 스파이크에는 제약을 걸 RDB가 없으므로 **여기가 유일한 방어**다.

**함정** 만료 쪽에서 자리를 비우려면 `userId`가 필요한데 그 정보가 `req:` 안에만 있다. **메모를 지우기 전에 먼저 읽어야 한다.**

## 13. 요청 ID와 신청 시각을 클라이언트가 정하면 안 된다

**원인** 둘 다 4.3의 전순서를 이루는 값이다. 클라이언트가 보내면 먼저 신청한 사람을 제칠 수 있고, 요청 ID는 중복도 막아야 하는데 그건 서버만 보장할 수 있다.

**결정** `requestId`는 Redis `INCR`(원자적, 인스턴스 몇 대든 중복 없음), `requestedAt`은 `RedisClock`. 요청 본문에는 이 둘이 아예 없다(`MatchRequestBody`).

## 14. 확정한 인스턴스와 연결된 인스턴스가 다르다 — SSE

**원인** `02` 1.1 — SSE 연결은 한 인스턴스에 고정된다. `MatchingTick`이 직접 `SseEmitter`를 찾으면 자기에게 붙은 사용자만 알림을 받는다.

**결정** Redis Pub/Sub. 확정한 인스턴스가 발행하고, 모든 인스턴스가 구독해 **자기에게 붙은 사용자의 것만** 내보낸다.

채널은 하나(`matching:events`)만 쓴다. 사용자별 채널을 두면 인스턴스가 받는 양이 줄지만 연결이 붙고 끊길 때마다 구독을 붙였다 떼야 하고, 그 관리가 틀리면 소식이 **조용히 사라진다.** 조용한 실패는 찾기 어렵다.

**순서** 발행은 저장이 끝난 **뒤에**(`02` 3.2). 먼저 알리면 확정에 실패했는데 "파티가 잡혔다"는 소식이 이미 나간 상태가 된다. 만료도 같고, 만료는 알리려면 조건을 알아야 하므로 **메모를 지우기 전에 읽어야** 한다.

---

## 15. 순서가 깨져도 덜 아픈 쪽으로 — 쓰기 순서 규칙

여러 곳에서 같은 원리가 반복됐다. 한데 모아둔다.

| 상황 | 순서 | 반대로 하면 |
|---|---|---|
| 요청 등록 | 메모 → 명단 | 조건을 읽을 수 없는 요청이 잠깐 후보가 됨 |
| 요청 삭제 | 명단 → 메모 | 위와 같음 |
| 파티 확정 | claim → 명단 → 메모 → 가드 → 발행 → release | 중복 배정 / 확정 실패한 파티의 알림 |
| 틱 한 바퀴 | 시계 한 번 → 만료 → 매칭 | 조합마다 만료 기준이 달라짐 / 만료자가 파티에 들어감 |

공통 원칙은 **"명단에 있는 요청은 항상 메모가 있다"**를 유지하는 것이다. 중간에 죽어도 남는 쪽이 고아 메모여야지, 조건 없는 명단 항목이면 안 된다.

## 17. 배경 스케줄러가 다른 테스트의 명단을 먹었다

## 18. 테스트가 시계를 두 번 읽어 틀린 기대를 했다

**증상**
```
Expecting actual:  [10L, 9L]
to contain exactly: [9L, 10L]
```
6번과 같은 모양이라 패딩 버그가 재발한 줄 알았다.

**원인** 헬퍼가 부를 때마다 `clock.nowMillis()`를 다시 읽어서 두 요청의 신청 시각이 실제로 달랐다. 10번이 먼저 등록됐으니 신청 시각도 더 이르고, `[10, 9]`가 **맞는 결과**였다. 코드가 아니라 테스트가 틀렸다.

**잠금** 시각을 직접 넘기는 `requestAt` 헬퍼를 따로 두고, `requestFrom`의 javadoc에 함정을 적었다.

## 19. Boot 4에 MockMvc 테스트 지원이 없다

**증상** `@AutoConfigureMockMvc`를 못 찾는다. Boot 4가 모듈을 잘게 쪼개면서 기본 의존성에서 빠졌다.

**결정** 의존성을 추가하는 대신 `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `RestClient`로 **실제 HTTP**를 쏜다. 실제 톰캣이 뜨고 실제 JSON이 오가니 계약 검증에는 오히려 맞다. `RestClient`는 4xx에 예외를 던지므로 `defaultStatusHandler`로 껐다 — 상태 코드 자체가 검사 대상이다.

**곁가지** `LocalServerPort`도 위치가 바뀌었다: `org.springframework.boot.test.web.server.LocalServerPort`.

## 20. SSE 타임아웃이 테스트를 6분 42초 붙잡았다

**증상** SSE 테스트 하나 돌리는 데 6분 42초.

**원인** 연결 유지 시간을 `최대 대기시간 + 1분 = 6분`으로 잡아 뒀는데, 연결을 안 닫고 끝난 테스트를 그만큼 기다렸다.

**결정** `queuemate.matching.sse-timeout`으로 빼고 테스트에서는 5초. 운영 기본값이 최대 대기시간보다 긴 이유는 **만료 소식을 받을 연결이 먼저 닫히면 안 되기** 때문이다.

## 21. 싱글턴 등록소가 테스트끼리 샜다

**증상** `connectionCount(7L)`이 1이어야 하는데 3.

**원인** `EmitterRegistry`가 스프링 빈이라 앞 테스트에서 연 연결이 남아 있었다. 클라이언트가 끊어도 서버 쪽 `SseEmitter`는 타임아웃 전까지 살아 있다.

**결정** 테스트마다 다른 사용자 ID를 쓴다. 등록소를 비우는 메서드를 만들면 운영 코드에 테스트 전용 API가 생긴다.

## 22. `SseEmitter.complete()`는 콜백을 항상 울리지 않는다

**증상** `emitter.complete()` 후에도 등록소에서 안 빠진다.

**원인** 실제 HTTP 응답에 붙지 않은 `SseEmitter`는 완료 콜백을 울리지 않는다. 핸들러가 없으면 완료 표시만 남긴다.

## 23. 다른 세션의 작업을 덮어썼다

**증상** 틱 루프를 쓰던 중 컴파일이 깨졌다. 내가 만들지 않은 테스트 파일 셋(`MatchingRaceTest`, `MatchingLoadTest`, `MatchingCrashTest`)과 `blog/`, `measurements/`가 작업 트리에 있었고, `WaitingListTest`에 모르는 테스트가 들어 있었다.

**원인** 마지막 커밋(`e4449ee`) 이후 다른 세션이 "명단 삭제 방식 vs claim 방식" 비교 실험을 했다. 그 세션이 `WaitingList`에 추가한 `removeAll(List<Long>)`을, 내가 파일을 통째로 다시 쓰면서(`cat >`) 지웠다. **커밋되지 않은 변경이라 git으로 복구할 수 없었다.**

**결정** 내 변경을 스크래치패드로 빼고 → 커밋 상태로 되돌리고 → 테스트가 정의한 동작대로 `removeAll`을 다시 만들고 → 그쪽 작업을 먼저 커밋하고(`fa6e3a5`) → 내 작업을 그 위에 얹었다.

**교훈**
- 작업 시작 전에 `git status`를 본다.
- **파일을 통째로 덮어쓰지 않는다.** 부분 수정으로 바꿨다면 충돌이 났을 뿐 지워지지는 않았다.
- 테스트가 남아 있어 인터페이스를 복원할 수 있었다. 테스트가 명세 역할을 했다.

**남은 위험** 복원한 `removeAll`은 원본과 구현이 다를 수 있다(예: `ZREM` 반환값으로 세고 실패 시 `ZADD`로 되돌리는 방식). 측정 결과에 영향이 있는지 확인이 필요하다.

## 25. 두 인스턴스가 같은 파티를 각각 확정했다

**증상** 인스턴스 두 대를 실제로 띄우고 40명을 신청시켰더니 파티가 31개 나왔다. 40명이면 최대 20개다.

```
8081이 확정: 15개   8082가 확정: 16개
양쪽이 똑같이 확정한 파티: 15개
요청 30개가 각각 두 파티에 들어갔다
```

로그를 맞춰 보니 같은 파티를 4밀리초 차이로 양쪽이 확정하고 있었다.

```
app1  02:03:54.423  파티 성립: [9, 10]
app2  02:03:54.427  파티 성립: [9, 10]     ← 같은 파티
```

**원인** 배정 중 표시를 확정 직후 곧바로 풀었는데, 그 틈에 다른 인스턴스가 **이미 처리된 같은 파티**를 들고 와 표시를 새로 얻었다. 앞서 명단을 읽어 둔 상태라 그 요청들이 사라진 줄 몰랐다.

```
A: claimAll([9,10]) 성공 → 명단 제거 → 메모 삭제 → claim 해제   ← 여기가 문제
B: claimAll([9,10]) 성공 (A가 방금 풀었으므로)
   → 이미 빈 명단에서 제거 시도 (실패하지만 반환값을 안 봤다)
   → 그대로 확정하고 소식까지 발행
```

**진짜 원인은 반환값을 버린 것이다.** `WaitingList.removeAll`은 전원을 빼거나 아무도 빼지 않는 Lua 스크립트라 **원자적 심판**이 될 수 있는데, `MatchingTick.confirm`이 결과를 무시하고 진행했다.

**결정** 명단에서 빼내는 데 성공한 쪽만 확정한다.

```java
if (!waitingList.removeAll(partition, requestIds)) {
    return false;   // 남이 먼저 가져갔다. 아무것도 지우지 않았으니 다음 바퀴에 다시 후보가 된다
}
```

역할이 둘로 갈린다는 것이 이 문제의 교훈이다.

| | 역할 |
|---|---|
| `claim:{id}` | **최적화** — 헛일을 줄이고, 크래시 시 TTL로 회수한다 |
| 명단 삭제 | **정합성** — 같은 요청이 두 파티에 들어가지 않게 막는다 |

`02`가 "락은 최적화이고, 정합성은 제약이 보장한다"고 쓴 것과 같은 구조다. 여기서는 제약 자리에 원자적 명단 삭제가 있다.

**왜 테스트로 안 잡혔나** 인스턴스가 하나면 재현되지 않는다. 한 프로세스 안에서는 틱이 순차로 돌아 두 바퀴가 겹치지 않는다. **실제로 두 대를 띄워야만 보이는 문제였다.**

**잠금** `MatchingTickTest.twoInstancesNeverConfirmTheSameRequestTwice`(스레드 2개가 같은 명단으로 동시에 `runOnce`), `neverConfirmsWithoutWinningTheWaitingList`

**검증** 고친 뒤 다시 2대로 40명: 파티 20개, 배정 40명, 중복 0건, 남은 대기 0.

## 26. zsh 배열은 1부터 시작한다 — 측정 스크립트가 틀렸다

**증상** 40명 신청 중 8명이 400으로 거절됐다. "요청이 사라지나?" 하고 앱을 의심했다.

**원인** 확인용 셸 스크립트에서 `POS=(TOP JUNGLE MID BOTTOM SUPPORT)`를 `POS[$((i % 5))]`로 꺼냈다. bash는 0부터지만 **zsh는 1부터**라 `i % 5 == 0`인 8명이 빈 문자열을 주 포지션으로 보냈다. 앱은 정상적으로 400을 돌려준 것이다.

**교훈** 재현 스크립트가 틀렸을 가능성을 앱보다 먼저 의심한다. 이번에는 "40명 중 32명만 배정"이라는 숫자가 앱 버그(25번)와 겹쳐 보여 헷갈렸다.


## 27. 부하 테스트의 claim과 실제 루프의 claim이 다른 규율이었다

**증상** 25번(두 인스턴스가 같은 파티를 각각 확정)을 실제 구동에서 잡았는데, `MatchingLoadTest`는 claim 방식에 대해 **위반 0건**을 보고하고 있었다. 같은 방식인데 결과가 갈렸다.

**원인** 두 코드의 claim 다루는 방식이 달랐다.

```java
// MatchingLoadTest — 잡고 끝. 풀지 않는다. TTL이 알아서 푼다
case CLAIM -> claims.claimAll(memberIds).isPresent();

// MatchingTick(고치기 전) — 확정하자마자 풀었다
try { ...확정... } finally { claims.releaseAll(requestIds, owner); }
```

부하 테스트는 표시를 **TTL이 끝날 때까지 들고 있어서** 다른 인스턴스가 그 사이 같은 파티를 다시 잡을 수 없었다. 실제 루프는 곧바로 풀어 그 창이 열렸다.

즉 **부하 측정의 0건은 그 규율에서만 참**이었고, 실제 루프의 규율은 측정된 적이 없었다.

**결정** 25번의 고침(명단 삭제 결과를 심판으로 삼기)은 **표시를 언제 푸느냐와 무관하게** 안전하다. TTL에 기대는 것보다 낫다. 표시를 오래 들고 있으면 그 요청 ID가 그동안 묶이고, 취소·재신청이 막힌다.

**교훈** 측정 코드와 실제 코드가 같은 절차를 각자 구현하고 있으면, **측정이 참인 범위가 실제와 다를 수 있다.** 부하 테스트가 `MatchingTick`을 직접 부르지 않고 루프를 다시 짠 것이 원인이다. 세 방식(none·remove·claim)을 나란히 비교하려면 그래야 했지만, 그만큼 실제와 벌어질 여지가 생긴다.
