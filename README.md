# party-matcher

> 다중 제약 조건 하의 **실시간 파티 배정 시스템**.
> 조건이 맞는 사람을 서버가 묶어 확정한다. 도메인은 리그 오브 레전드 파티 매칭이다.

## 배경

같이 할 사람을 구하는 방식이 지금은 이렇게 생겼다.

```
디스코드 서버 입장 → 구인 글 작성 → 누군가 읽기를 기다림 → DM → 조건 확인 → 합류
```

각 단계가 사람이 응답할 때까지 멈춰 있다. 그래서 실제로는 대부분 **아는 사람에게 연락하거나, 혼자 랜덤 매칭을 돌린다.**
조건이 맞는 낯선 사람과 파티를 짜는 경로는 사실상 없다.

조건이라는 게 취향 문제가 아니라는 점이 이 문제의 성격을 정한다.
티어 범위, 포지션, 음성채팅 여부, 플레이 목적이 어긋나면 파티는 성립해도 그 판은 서로에게 손해다.
**매칭이 느린 게 문제가 아니라, 조건을 맞추는 비용이 커서 아무도 안 하는 것이다.**

## 문제 정의

**이건 게시판 문제가 아니라 배정(assignment) 문제다.**

한 사람의 요청을 조건이 맞는 후보 전원과 맞춰보고, 정원만큼 묶어 확정한다. 조율 단계가 없다.
그래서 게시판을 빠르게 만드는 것으로는 풀리지 않고, 다음을 풀어야 한다.

| # | 문제 | 성격 |
|---|---|---|
| 1 | 확정 파티의 **빈자리 하나에 여러 명이 동시 지원** | 좌석 경합 |
| 2 | 한 사람이 시간이 겹치는 **두 파티에 동시 배정** | 교차 제약 경합 |
| 3 | 00시 예약 배치가 **재실행·중복 실행돼도** 중복 배정 없어야 함 | 멱등성 |
| 4 | 제안 1건을 **서로 다른 인스턴스에 붙은** 참가자 전원에게 동시 전달 | 팬아웃 + 분산 전파 |
| 5 | 예약 알림을 걸고, 파티가 취소되면 **회수**하고, 두 번 보내지 않기 | 지연 큐 멱등성 |
| 6 | Riot API의 갱신 주기 · 동시 조회 · 레이트리밋 | 캐싱 + 호출 병합 |
| 7 | 5인 파티를 **주/부 포지션 제약 하에** 서로 다른 포지션으로 배정 | 조합 탐색 |

### 1·2번이 핵심이다

**2번은 이 서비스에 원래 있는 문제다.** 요청 하나가 동시에 두 후보 파티에 묶이면,
사용자는 같은 시간에 두 파티에 들어간다. 단일 행 카운터가 아니라 요청·시간·포지션이 얽힌
교차 제약이라, 재고 차감보다 제약을 표현하는 것 자체가 어렵다.

**1번은 빈자리 충원 때문에 생긴다.** 서버가 정원만큼 묶어 제안하고 전원 수락해야 확정하는 구조에서는
자리를 놓고 경쟁하는 사람이 없다. 정원 초과는 확정된 파티에서 이탈자가 나와
그 자리를 공개 모집할 때 비로소 발생한다. 5인 파티에서 한 명 빠졌다고 파티 전체를 버리는 건 낭비이므로
충원은 실제로 필요한 기능이고, 그 기능이 좌석 경합을 만든다.
빈자리는 포지션 단위로 열리므로, 경합 대상은 파티 정원이 아니라 **특정 포지션의 좌석 하나**다.

**3번은 성격이 다르다.** 예약 매칭은 **수락 없이 자동 확정**되므로, 배치가 두 번 돌면
사용자는 자기가 모르는 파티에 두 번 들어간다. 사후 취소로 수습할 수 없다.

## 전제

**애플리케이션 인스턴스 2대 이상을 전제로 설계한다.**

인스턴스가 하나면 애플리케이션 락만으로 1·2번이 막혀 문제가 재현되지 않는다.
재현되지 않으면 데이터베이스 제약과 분산 락이 왜 필요한지도 증명할 수 없다.
3·4·5번은 아예 인스턴스가 둘 이상일 때만 나타나는 문제다.

```
App × 2  ─┬─  RDB
          ├─  Redis (분산 락 / Pub/Sub / 지연 큐 / 캐시)
          └─  부하 발생기
```

## 접근

각 단계는 **틀린 구현을 먼저 만들어 깨지는 것을 확인한 뒤** 고친다. 수치 없이 넘어가지 않는다.

| 단계 | 과제 | 대응 문제 | 상태 |
|:---:|---|:---:|:---:|
| 0 | 도메인 모델 · 상태 기계 · 부하 발생기 · 위반 검출기 | — | 예정 |
| 1 | 무제어 빈자리 충원 — **정원 초과 재현** | 1 | 예정 |
| 2 | 제어 전략 비교 — 비관적 락 · 낙관적 락 · 파티션 단일 라이터 | 1 | 예정 |
| 3 | 중복 배정 차단 — 제약 위치 결정 (DB 제약 vs 애플리케이션) | 2 | 예정 |
| 4 | 예약 배치 멱등성 — 재실행 · 중복 실행 · **락 만료 중 작업 지속** | 3 | 예정 |
| 5 | 제안 팬아웃 · 만료 · 인스턴스 간 전파 · 재연결 복구 | 4 | 예정 |
| 6 | 알림 지연 큐 — 예약 · 회수 · 중복 발송 차단 | 5 | 예정 |
| 7 | 외부 API 캐싱 · 동시 조회 병합 · **캐시 스탬피드** · 레이트리밋 | 6 | 예정 |
| 8 | 포지션 배정 — 이분 매칭과 가지치기 | 7 | 예정 |
| 9 | 전 구간 요청 추적 (요청 1건의 매칭 경로 복원) | 전체 | 예정 |

> 2단계는 락 전략만 비교하지 않는다. 매칭은 원래 단일 라이터로 짜는 게 자연스러운 문제이므로,
> **게임·모드 단위 파티션 + 순차 처리**를 비교군에 포함해 처리량·지연·구현 복잡도로 함께 잰다.
>
> 9단계는 "왜 나는 매칭이 안 됐나"라는 문의가 들어왔을 때,
> 그 요청이 어느 조건에서 걸러졌는지 로그로 복원할 수 있어야 한다는 요구에서 나온다.

## 측정 방식

- **통과 게이트** — 정원 초과, 중복 배정, 알림 중복 발송. 비교 지표가 아니다. 0이면 통과, 1건이라도 있으면 탈락.
- **비교 지표** — 처리량, p95 응답시간, 외부 API 호출 수. 같은 조건에서 Before/After를 잰다.
- **위반 검출은 로그가 아니라 데이터베이스를 직접 검사해서 계수한다.** 위반이 발생했는데 로그에 안 남는 경우가 가장 위험하다.
  검사 술어는 [기술 보완 명세 2장](docs/02-technical-spec-supplement.md)에 불변식별로 정의한다.
- 실제 이용자를 전제하지 않고 **합성 부하**로 측정한다. 같은 씨드값으로 같은 부하를 재현한다.
  씨드값은 재현성만 보장하므로, **입력 분포**를 함께 고정하고 균등 분포와 실제 티어 분포 두 조건에서 잰다.
- **매칭 성립률 곡선** — 동시 대기자 10 / 30 / 50 / 100 / 200명 구간에서 성립률과 평균 대기시간을 잰다.
  조건을 전부 필수로 처리하는 방식이 실용 수준에 도달하는 지점을 찾고, 조건 완화 도입 근거로 쓴다.

## 범위

**MVP는 리그 오브 레전드 하나만 지원한다.**

매칭은 밀도가 전부라, 게임을 늘리면 대기자가 갈라져 성립률이 떨어진다.
게임별로 연동·오류 분기·조건 스키마가 달라 구현 시간도 늘어나며, 그 시간은 동시성 과제에서 빠져나간다.
게임 추가는 코드가 아니라 **설정으로 처리할 수 있게 설계**하되, MVP에서는 롤 하나만 등록한다.

- 신원은 **Discord 계정**으로 확인한다. 익명 식별자를 쓰지 않으므로 기기를 바꿔도 상태가 이어진다.
- 티어는 Riot API에서 조회한 실제 값이다. 자기 신고가 아니다.
  다만 입력한 Riot ID가 본인 계정인지는 검증하지 못하며, 이 한계를 화면에 표시한다.
- 알림은 Discord 다이렉트 메시지로 보낸다. Web Push는 쓰지 않는다.

제외 — PUBG · Steam 게임, Riot Sign On, Discord 전용방 자동 생성, 일치도 점수,
조건 자동 완화, 반복 예약, 신고 · 내부 신뢰도 점수, 운영자 화면.

평가 · 차단 · 재회는 **포함한다.** 조건만으로 만난 사람과 다시 만날 수 없으면 이 서비스는
일회용이 된다. 재회는 조건을 완화하지 않고 **통과한 후보 안에서 순서만 앞당긴다.**

## 외부 연동

- **Riot API** — 개발 단계는 24시간마다 만료되는 개발용 키를 사용한다.
  Personal key 승인 후 키만 교체하며 코드는 바꾸지 않는다.
  Personal key와 개발용 키 모두 **공개 서비스 운영이 허용되지 않으므로**, MVP 단계에서는 공개 배포하지 않는다.
- **Discord** — OAuth2로 신원을 확인하고 Bot으로 다이렉트 메시지를 보낸다.
