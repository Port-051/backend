# game-party-matcher

> 롤·PUBG·Steam 멀티플레이 게임의 파티를, 조건이 맞는 사람끼리 **자동으로 묶어 확정**하는 매칭 API.

---

## 배경

같이 할 사람을 구하는 방식이 지금은 이렇게 생겼다.

```
디스코드 서버 입장 → 구인 글 작성 → 누군가 읽기를 기다림 → DM → 조건 확인 → 합류
```

각 단계가 사람이 응답할 때까지 멈춰 있다. 그래서 실제로는 대부분 **아는 사람에게 연락하거나, 혼자 랜덤 매칭을 돌린다.**
조건이 맞는 낯선 사람과 파티를 짜는 경로는 사실상 없다.

조건이라는 게 취향 문제가 아니라는 점이 이 문제의 성격을 정한다.
티어 범위, 포지션, 음성채팅 여부, 플레이 목적(랭크 상승인가 가볍게 즐기기인가)이 어긋나면
파티는 성립해도 그 판은 서로에게 손해다. **매칭이 느린 게 문제가 아니라, 조건을 맞추는 비용이 커서 아무도 안 하는 것이다.**

## 문제 정의

**이건 게시판 문제가 아니라 배정(assignment) 문제다.**

한 사람의 요청을 조건이 맞는 후보 전원과 맞춰보고, 정원만큼 묶어 확정한다. 조율 단계가 없다.
그래서 게시판을 빠르게 만드는 것으로는 풀리지 않고, 다음을 풀어야 한다.

| # | 문제 | 성격 |
|---|---|---|
| 1 | 자리는 N개인데 여러 명이 **동시에 수락** | **동시성 제어** |
| 2 | 한 사람이 **두 파티에 동시 배정** | 교차 자원 경합 |
| 3 | 00시 예약 배치가 **재실행돼도** 중복 배정 없어야 함 | 멱등성 |
| 4 | 제안 1건을 참가자 전원에게 동시 전달하고 제한시간에 만료 | 팬아웃 + 만료 |
| 5 | Riot·PUBG·Steam 3종 외부 API의 갱신 주기·동시 조회·레이트리밋 | 캐싱 + 호출 병합 |
| 6 | 로그인이 없어 상태가 브라우저에 묶임 | 익명 식별자 생명주기 |

1·2번이 이 서비스의 핵심이다. 정원을 넘겨 확정하면 누군가는 자리가 없다는 말을 듣게 되고,
**한 번 겪으면 다시 쓰지 않는다.** 재고 차감과 같은 문제이되 자원이 사람이라 실패 비용이 크다.

3번은 성격이 다르다. 예약 매칭은 **수락 없이 자동 확정**되므로, 배치가 두 번 돌면
사용자는 자기가 모르는 파티에 두 번 들어간다. 사후 취소로 수습할 수 없다.

## 접근

각 단계는 **틀린 구현을 먼저 만들어 깨지는 것을 확인한 뒤** 고친다. 수치 없이 넘어가지 않는다.

| 단계 | 과제 | 대응 문제 | 상태 |
|:---:|---|:---:|:---:|
| 0 | 도메인 모델 · 측정 하네스 (요청 / 제안 / 파티) | — | 예정 |
| 1 | 락 없는 수락 — **정원 초과 재현** | 1 | 예정 |
| 2 | 동시성 제어 적용 및 비교 | 1 | 예정 |
| 3 | 중복 배정 차단 — 제약 위치 결정 (DB 제약 vs 애플리케이션) | 2 | 예정 |
| 4 | 예약 배치 멱등성 — 재실행·중복 실행 시나리오 | 3 | 예정 |
| 5 | 제안 팬아웃과 만료 처리 | 4 | 예정 |
| 6 | 외부 API 캐싱·동시 호출 병합·레이트리밋 대응 | 5 | 예정 |
| 7 | 전 구간 요청 추적 (요청 1건의 매칭 경로 복원) | 전체 | 예정 |

> 7단계의 기준: "왜 나는 매칭이 안 됐나"라는 문의가 들어왔을 때, 그 요청이 어느 조건에서 걸러졌는지 로그로 복원할 수 있어야 한다.

## 측정

- 지표: 정원 초과 건수, 중복 배정 건수, 매칭 처리량, p95 응답시간
- 각 단계는 **Before/After를 같은 조건에서** 재고, 측정 환경(머신 사양·부하 도구 옵션·커넥션 풀 크기)을 결과와 함께 기록한다
- 정원 초과·중복 배정은 비교 지표가 아니라 **통과 게이트**로 쓴다 — 0이면 통과, 1건이라도 있으면 탈락

## 범위

MVP는 **로그인 없이 즉시 이용 / 즉시 매칭 + 일회성 예약 / Discord 전용방 자동 생성**까지다.
일치도 점수, 조건 자동 완화, 반복 예약, 평가·차단·신고, 운영자 화면은 제외한다.
자세한 제외 목록은 명세서 14장에 있다.
