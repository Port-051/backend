# 테스트가 다 통과하는데 실제로 띄우니 중복 배정이 났습니다 (Redis · 분산)

[지난 글](01-matching-concurrency.md)에서 매칭 루프의 동시성 제어를 두 방식으로 재고 `claim`을 골랐습니다. 부하 표에서도, 장애 표에서도 중복 배정은 0이었습니다.

그 뒤 HTTP API와 실시간 알림을 붙이고, 처음으로 **인스턴스 두 대를 실제로 띄워** 사람 마흔 명을 신청시켰습니다. 파티가 서른한 개 나왔습니다. 마흔 명이면 최대 스무 개입니다.

이 글은 그 버그를 찾고 고친 기록이자, **왜 제 테스트들이 그것을 놓쳤는지**에 대한 기록입니다. 후자가 본론입니다.

---

## 통과하고 있던 것들

버그를 찾기 직전의 상태는 이랬습니다.

- 단위·통합 테스트 **171개 전부 통과**
- 부하 측정: 인스턴스 8대까지 **중복 배정 0건**
- 장애 측정: 확정 중 프로세스를 죽여도 **요청 증발 0%**

부하 표에서 `claim` 행은 이렇게 나왔습니다.

| 인스턴스 | 유입 | 성립한 파티 | 중복 배정 | 위반율 |
|---:|---:|---:|---:|---:|
| 2 | 2501 | 1250 | 0 | 0.0000 |
| 4 | 2501 | 1250 | 0 | 0.0000 |
| 8 | 2501 | 1250 | 0 | 0.0000 |

선점을 아예 끄면 위반율이 99% 넘게 나오는 표였으니, 0.0000이 우연일 리는 없어 보였습니다.

---

## 실제로 띄웠습니다

같은 jar를 포트만 바꿔 두 개 띄우고, Redis 하나를 공유하게 했습니다.

```bash
java -jar queuemate.jar --server.port=8081 &
java -jar queuemate.jar --server.port=8082 &
```

마흔 명이 번갈아 두 인스턴스에 신청합니다. 조건은 전부 서로 맞게 두었으니 2인 파티 스무 개가 나와야 합니다.

```
신청 40명 → 기대 파티 20개
8081: 15   8082: 16
배정 슬롯 62 / 서로 다른 요청 32
중복: 30 건
```

**요청 서른 개가 각각 두 파티에 들어가 있었습니다.**

두 로그를 시각으로 맞춰 보니 답이 나왔습니다.

```
app1  02:03:54.423  파티 성립: [9, 10]
app2  02:03:54.427  파티 성립: [9, 10]
```

같은 파티를 4밀리초 차이로 양쪽이 확정하고 있었습니다. 8081이 만든 열다섯 개는 **전부** 8082 것과 같은 조합이었습니다.

## 원인: 표시를 너무 일찍 풀었습니다

확정 코드는 이랬습니다.

```java
Optional<String> owner = claims.claimAll(requestIds);
if (owner.isEmpty()) {
    return false;
}

try {
    waitingList.removeAll(partition, requestIds);   // 반환값을 버렸습니다
    requestStore.deleteAll(requestIds);
    events.publishAll(MatchingEvent.confirmed(party));
    return true;
} finally {
    claims.releaseAll(requestIds, owner.get());     // 끝나자마자 풀었습니다
}
```

표시를 떼지 않으면 그 요청 ID가 유지 시간 동안 묶입니다. 확정이 끝났으면 풀어 주는 게 맞다고 생각했습니다.

그런데 그 사이에 다른 인스턴스가 **이미 처리된 같은 파티**를 들고 옵니다.

```
A: 명단 읽음 → [9,10] 계산
B: 명단 읽음 → [9,10] 계산      매처가 결정적이라 같은 답이 나옵니다

A: claimAll([9,10]) 성공
A: 명단에서 제거, 메모 삭제, 확정 알림
A: claim 해제                    ← 여기

B: claimAll([9,10]) 성공         A가 방금 풀었으니 잡힙니다
B: removeAll([9,10]) 실패        이미 비었지만 반환값을 안 봤습니다
B: 확정 알림                     같은 파티가 두 번 확정됐습니다
```

B는 **자기가 읽은 시점의 명단**을 들고 있습니다. 그 요청들이 이미 사라졌다는 사실을 모릅니다. 표시가 다시 잡히는 순간, B에게는 아무것도 이상하지 않습니다.

지난 글에서 결정성이 문제의 원인이라고 썼는데, 여기서도 같습니다. **두 인스턴스가 반드시 같은 답을 내기 때문에** 충돌이 우연이 아니라 필연입니다.

---

## 그런데 왜 측정에서는 안 나왔을까

이 질문이 이 글의 이유입니다. 부하 테스트는 인스턴스를 여덟 대까지 늘리고도 0건을 보고했습니다.

측정 코드를 다시 읽어 보니, 선점을 이렇게 하고 있었습니다.

```java
private boolean take(Guard guard, List<Long> memberIds) {
    return switch (guard) {
        case NONE   -> true;
        case REMOVE -> waiting.removeAll(PARTITION, memberIds);
        case CLAIM  -> claims.claimAll(memberIds).isPresent();
    };
}
```

**표시를 잡고 풀지 않습니다.** 유지 시간이 끝날 때까지 들고 있습니다.

그래서 측정에서는 B가 같은 파티를 다시 잡을 수 없었습니다. A가 확정한 뒤에도 표시가 몇 초간 남아 있으니까요. 그 사이에 그 요청들은 명단에서도 사라지고, 다시는 후보가 되지 않습니다.

즉 표의 0.0000은 **틀린 값이 아니라, 측정한 적 없는 규율에 대한 값**이었습니다.

```
측정 코드:  잡고 → 안 푼다 (유지 시간에 맡긴다)
실제 코드:  잡고 → 확정하고 → 곧바로 푼다
```

같은 `claim` 방식이라고 불렀지만 규율이 달랐고, 갈리는 지점이 정확히 버그가 사는 곳이었습니다.

원인은 분명합니다. **측정 코드가 실제 매칭 루프를 부르지 않고 루프를 다시 구현했습니다.** 세 방식(선점 없음·명단 삭제·표시)을 한 표에 나란히 놓으려면 그래야 했습니다. 절차를 전부 같게 두고 선점 한 줄만 바꿔야 표의 차이를 선점 탓으로 읽을 수 있으니까요.

그 대가로 측정 대상과 배포 대상이 벌어졌습니다.

## 고침: 심판을 옮겼습니다

표시를 더 오래 들고 있는 것도 방법입니다. 유지 시간을 늘리면 B가 다시 잡지 못합니다.

하지만 그러면 정확성이 **시간 설정에 의존**하게 됩니다. 유지 시간이 짧으면 깨지고, 길면 취소나 재신청이 그만큼 막힙니다. 그리고 얼마가 충분한지 답할 방법이 없습니다.

대신 이미 있던 값을 쓰기로 했습니다.

```java
if (!waitingList.removeAll(partition, requestIds)) {
    return false;
}
```

`removeAll`은 전원을 빼거나 아무도 빼지 않는 Lua 스크립트입니다. 지난 글에서 "명단 삭제" 방식으로 재던 바로 그 연산입니다. **원자적이므로 성공하는 쪽은 정확히 하나**입니다.

한 줄입니다. 반환값을 버리고 있었을 뿐입니다.

이제 표시를 언제 풀든 상관없습니다. B가 표시를 다시 잡아도 명단에서 빼지 못하면 확정하지 않습니다.

## 역할이 둘로 갈립니다

고치고 나서 정리된 그림이 이렇습니다.

| | 역할 | 없으면 |
|---|---|---|
| `claim` 표시 | **최적화** | 헛일이 늘고, 확정 중 죽으면 요청을 잃습니다 |
| 명단 삭제 | **정합성** | 같은 요청이 두 파티에 들어갑니다 |

지난 글에서 두 방식을 **경쟁 관계**로 재고 하나를 골랐는데, 실은 층이 달랐습니다. 표시는 경합을 줄이고 크래시를 회수하는 장치이고, 중복을 막는 것은 명단 삭제입니다. 둘 다 필요합니다.

기술 문서에 이런 문장이 있습니다.

> 락은 최적화이고, 정합성은 제약이 보장한다.

읽을 때는 당연한 말로 넘겼는데, 제 코드는 락에 정합성을 맡기고 있었습니다.

## 다시 재보기

같은 조건으로 두 대를 다시 띄웠습니다.

```
신청 40명 → 기대 파티 20개
8081: 10   8082: 10
배정 슬롯 40 / 서로 다른 요청 40
중복: 0 건
남은 대기: 0
```

마흔 명이 스무 파티에 정확히 한 번씩 들어갔습니다.

회귀 테스트도 걸었습니다. 스레드 두 개가 같은 명단으로 동시에 한 바퀴를 돌립니다.

```java
Future<List<Party>> left  = pool.submit(() -> { start.await(); return tick.runOnce(); });
Future<List<Party>> right = pool.submit(() -> { start.await(); return tick.runOnce(); });
start.countDown();

List<Long> assigned = Stream.concat(left.get().stream(), right.get().stream())
        .flatMap(party -> party.members().stream())
        .map(MatchRequest::requestId)
        .toList();

assertThat(assigned).doesNotHaveDuplicates();
assertThat(assigned).hasSize(20);
```

한 프로세스 안이지만 두 바퀴가 실제로 겹쳐 돌기 때문에 이 버그를 잡습니다. 고치기 전 코드로 되돌리면 빨간불이 켜집니다.

## 마치며

세 가지가 남았습니다.

**통과하는 테스트의 개수는 아무것도 보장하지 않습니다.** 171개가 통과했고 그중 상당수가 진짜 Redis를 띄워 도는 통합 테스트였습니다. 그래도 이 버그는 인스턴스가 하나뿐인 곳에서는 재현되지 않습니다. 한 프로세스 안에서는 틱이 순차로 돌아 두 바퀴가 겹치지 않기 때문입니다.

**측정 코드가 실제 코드와 다르면, 측정은 실제에 대해 아무 말도 하지 않습니다.** 그리고 다르다는 사실 자체가 잘 안 보입니다. 양쪽 다 `claim`을 부르고 있었고, 이름도 같았고, 절차도 같아 보였습니다. 갈린 곳은 "언제 푸느냐" 한 줄이었습니다.

**정합성을 시간에 맡기지 말아야 합니다.** 유지 시간을 늘리는 것도 이 버그를 없앱니다. 다만 얼마가 충분한지 답할 수 없고, 부하가 바뀌면 다시 깨집니다. 원자적 연산은 그런 질문을 만들지 않습니다.

### 아직 못 잰 것

- 고친 뒤의 부하 표입니다. 지금 표는 측정 코드가 여전히 자기 루프를 돌기 때문에 실제 루프의 숫자가 아닙니다. 측정이 `MatchingTick`을 직접 부르게 바꾸면 세 방식을 나란히 놓을 수 없어, 표를 포기할지 실제성을 포기할지 정해야 합니다.
- 인스턴스를 늘렸을 때의 헛일입니다. 여덟 대에서 파티 하나당 열 번꼴로 선점에 실패하는데, 명단을 조합별로 나눠 인스턴스마다 전담시키면 그 경합이 사라집니다. 구현 복잡도까지 함께 재야 합니다.
- 실제 네트워크 위의 지연입니다. 이번 두 인스턴스도 같은 기계 위에 있었습니다.

### 이 숫자의 한계

인스턴스 두 대는 같은 노트북의 프로세스 두 개입니다. Redis도 같은 기계의 컨테이너입니다. 그래서 4밀리초라는 간격은 실제 배포 환경의 값이 아닙니다. 다만 **버그의 존재 여부**는 간격과 무관합니다. 창이 좁아지면 확률이 낮아질 뿐, 사라지지 않습니다.
