# 판정 시나리오 제안 — 스파이크 #48

> **여운호 제안 · 2026-08-28.** 팀 합의 전이므로 확정이 아니다.
> 합의되면 규약 10절에 따라 **`main`에 먼저 넣는다** — "판정 시나리오는 같은 입력 대본.
> 문서로 적어 `main`에 먼저 넣는다."

이슈 #48의 미체크 항목 **"k6 시나리오 숫자 확정 — 도착률 · 티어 분포 · 실행 시간"**에 대한 안이다.

## 0. 왜 지금 정해야 하나

이슈 #48이 직접 적어놨다.

> **k6 시나리오 숫자는 시작 전에 확정해 문서로 넣는다.**
> 서로 다른 자로 잰 값은 비교가 되지 않는다.

지금 안 정하면 판정일에 이렇게 된다 — 셋이 각자 다른 도착률·다른 티어 분포·다른 실행 시간으로 재 오고,
판정 절차 2번(**같은 k6 시나리오로 매칭 성립률 · p95 지연**)이 통째로 성립하지 않는다.
그러면 남는 판정 근거는 불변식 위반 여부와 코드 읽기뿐이다.

**이미 낭비가 났다.** 나는 도착률 30/s·60/s로 재 뒀는데, 이 숫자가 합의되지 않으면 버려진다.

## 1. 고정할 것과 갈라놓을 것을 먼저 가른다

이게 제일 중요하다. **부하의 입력은 고정하고, 구현 선택은 고정하지 않는다.**

| 고정한다 — 부하의 입력 | 왜 |
|---|---|
| 도착률 · 동시 대기자 수 | 다르면 다른 것을 잰 값이다 |
| 실행 시간 | 짧으면 워밍업이, 길면 정상 상태가 섞인다 |
| 티어 분포 · 포지션 선호 | 02번 6.3 — "씨드는 재현성을 보장하지 타당성을 보장하지 않는다" |
| 씨드 | 같은 씨드면 같은 부하가 재현된다 |
| 개인 수락률 | 5인 파티는 한 명만 거절해도 깨진다. 이게 다르면 성립률 비교가 무의미하다 |
| **최대 대기시간** | 성립률의 분모를 정하는 값이다. 아래 3절 |
| 인스턴스 수 | 02번 1.2 — "1대 측정값은 비교군으로도 쓰지 않는다" |

| **고정하지 않는다** — 비교 축 | 왜 |
|---|---|
| 틱 주기 | 05번 자율. "루프를 언제 돌릴지"가 비교 대상이다 |
| 한 번에 읽는 인원 수 | 05번 자율. 처리량 축 |
| claim 자료구조 · TTL · 떼는 시점 | 05번 자율. 좌석 선점 단위와 락 범위 |
| Lua를 몇 개로 쪼갤지 | 05번 자율 |
| 파티션 단일 라이터 여부 | 02번 1.4가 비교 대상으로 남겼다 |

> **이 표를 헷갈리면 스파이크가 무너진다.** 틱 주기까지 고정하면 비교할 것이 코드 스타일만 남고,
> 도착률을 자율로 두면 애초에 비교가 안 된다.

**애매한 것 하나 — 제안 수락 제한시간(offer TTL).** 05번은 "제안 수명"을 자율로 뒀지만,
이 값이 짧으면 부하 스크립트가 응답하기 전에 시간초과돼 성립률이 구현과 무관하게 떨어진다.
**자율로 두되 하한 10초를 건다**고 제안한다. 부하 스크립트 폴링 주기(250ms)와 SSE 전달 지연을
감안해도 응답할 시간이 남아야 공정하다.

## 2. 실측 근거 — 성립률 곡선을 먼저 그려봤다

숫자를 감으로 제안하지 않으려고 `fill-rate-curve.js`로 실제로 쟀다.
인스턴스 2대 + nginx LB, 티어 분포 `real`, 개인 수락률 90%, 최대 대기시간 45초, 각 구간 75초.

### 자유 랭크 · 정원 5 (검증 P0)

| 동시 대기자 | 성립률 | 확정까지 평균 | 요청 생성 p95 |
|---:|---:|---:|---:|
| 10 | **0.0 %** | — | 22.1 ms |
| 30 | **0.0 %** | — | 14.8 ms |
| 50 | 22.7 % | 18.7 s | 18.3 ms |
| 100 | 57.0 % | 13.7 s | 19.4 ms |
| 200 | **77.5 %** | 11.4 s | 22.8 ms |

### 솔로·듀오 랭크 · 정원 2 (제품 P0)

| 동시 대기자 | 성립률 | 확정까지 평균 |
|---:|---:|---:|
| 50 | **96.0 %** | 4.2 s |

### 이 곡선이 말하는 것

**ㄱ. 02번 6.3이 찾으라고 한 지점이 나왔다.**
그 절은 "조건을 전부 필수로 처리하는 방식이 **실용 수준에 도달하는 지점**을 찾고,
조건 완화 도입 근거로 쓴다"고 했다. 정원 5에서 그 지점은 **동시 대기자 50~100 사이**다.
30명까지는 파티가 한 건도 성립하지 않는다.

**ㄴ. 정원이 성립률을 지배한다.**
같은 대기자 50명에서 정원 2는 96%, 정원 5는 22.7%다. PRD 5.2가 적어둔 그대로다 —
"정원 2는 후보 1명만 찾으면 되고, 정원 5는 4명을 동시에 찾아야 하며 포지션까지 겹치지 않아야 한다."

**ㄷ. 02번 6.4의 목표가 유효한 조건에서 실제로 통과했다.**
목표는 "매칭 요청 생성 p95 200ms 이하 — **인스턴스 2대, 동시 대기자 200명 구간**"인데,
그 구간에서 **22.8ms**가 나왔다. 목표에 20배 여유가 있다.

> ⚠️ 이 수치는 **내 구현 한 벌로 잰 것**이다. 판정용 기준선이 아니라
> "이 정도 구간을 잡으면 의미 있는 차이가 보인다"는 근거로만 쓴다.

## 3. 최대 대기시간을 45초로 줄이자 — 이게 제일 큰 제안

현재 설정은 5분이다(`queuemate.matching.max-wait`). **측정용으로는 45초를 제안한다.**

**이유 ㄱ — 5분이면 판정일에 곡선을 못 그린다.**
성립률의 분모는 "끝난 요청"이고, 파티가 안 된 요청은 최대 대기시간이 지나야 끝난다.
5분이면 구간 하나가 정상 상태에 닿는 데 10분 넘게 걸리고, 다섯 구간 × 두 큐면 두 시간이 넘는다.
판정일 하루에 셋이 각자 돌려야 한다.

**이유 ㄴ — 5분은 제품 현실과도 안 맞는다.**
PRD 6.1이 진입을 10초로 제약하며 적었다 — "**빡친 사람은 폼을 채우지 않는다**".
솔랭 한 판 망하고 들어온 사람이 5분을 기다리지 않는다. 45초가 오히려 시나리오에 가깝다.

**이유 ㄷ — 이 값은 구현 선택이 아니라 부하의 입력이다.**
틱 주기와 달리 최대 대기시간은 각자 다르게 정할 이유가 없고,
다르면 성립률의 분모가 달라져 비교가 깨진다.

`compose.yaml`에 오버라이드를 넣어 뒀다 — `MAX_WAIT=45s docker compose up -d`.

## 4. 제안하는 숫자

### 공통 — 전 시나리오에 똑같이 건다

| 항목 | 값 | 근거 |
|---|---|---|
| 구성 | 인스턴스 **2대** + nginx LB + Redis 1대 | 02번 1.2 |
| 씨드 | `20260828` | 04번 4.2 |
| 티어 분포 | **`real`과 `uniform` 둘 다** 돌리고 둘 다 리포트 | 02번 6.3 |
| 포지션 선호 | 탑 .26 / 정글 .16 / 미드 .30 / 바텀 .20 / 서폿 .08 | 02번 6.3 "서포터·정글 지원이 적은 실제 경향" |
| 개인 수락률 | **90 %** (거절 10 %) | 아래 ⚠️ |
| 최대 대기시간 | **45 s** | 3절 |
| 제안 수락 제한시간 | 자율, **하한 10 s** | 1절 |
| 폴링 주기 | 250 ms | SSE가 stock k6에 없어 폴링으로 대체한 결과 |

### 시나리오 A — 지연과 처리량 (open model)

`matching-load.js` · `constant-arrival-rate` · 04번 4.3이 고정한 모델

| 항목 | 값 |
|---|---|
| 도착률 | **30 /s** 와 **60 /s** 두 지점 |
| 실행 시간 | 각 **60 s** (앞 15초는 워밍업으로 버린다) |
| 큐 · 정원 | 자유 랭크 · 5 |
| 재는 것 | 요청 생성 p95 · 제안 전달 지연 p95 · 불변식 |

### 시나리오 B — 성립률 곡선 (closed model)

`fill-rate-curve.js` · `constant-vus` · 04번 4.3이 명시한 **예외**

| 항목 | 값 |
|---|---|
| 동시 대기자 | **10 / 30 / 50 / 100 / 200** |
| 실행 시간 | 각 **75 s** |
| 큐 · 정원 | 자유 랭크 · 5 **와** 솔로·듀오 · 2 |
| 재는 것 | 성립률 · 확정까지 평균과 p95 |

> 이 시나리오만 closed model인 이유는 "동시 대기자 N명"이 측정 조건 자체이기 때문이다.
> 리포트에 **어느 모델로 쟀는지 반드시 표기한다**(04번 4.3).

### 시나리오 C — 통과 게이트

| 항목 | 값 |
|---|---|
| 기능 인수 | `acceptance.py` 29개 — 명세 조항 단위 |
| 불변식 | `verify-invariants.py` — INV-2·3·4 각 0건 |
| 판정 | **성능과 무관하게 탈락 조건**이다 |

### 총 소요

시나리오 A 2회 × 60s + B 10회 × 75s + C ≈ **한 사람당 약 20분.**
셋이 각자 돌려도 판정일 오전 안에 끝난다.

## 5. ⚠️ 근거가 약한 숫자 셋 — 여기를 먼저 따져 달라

정직하게 적는다. 아래 셋은 **내 추정값**이고 실제 데이터가 없다.

| 값 | 지금 근거 | 위험 |
|---|---|---|
| 개인 수락률 90 % | 없음. 감이다 | 5인 파티 성립률은 대략 `0.9⁵ = 59%`로 눌린다. 이 값 하나가 곡선 전체를 좌우한다 |
| `real` 티어 분포 비율 | 없음. 아이언 10 / 브론즈 18 / 실버 22 … 추정 | 실제 분포가 더 몰려 있으면 성립률이 올라간다 |
| 포지션 선호 가중치 | 없음. "서폿이 적다"는 통념 | 서폿 비율이 성립률을 직접 결정한다 — 5인 파티에 서폿이 반드시 한 명 필요하다 |

**셋 다 실제 데이터로 대체할 수 있으면 좋지만, 못 구하면 그냥 값을 고정하고 넘어가도 된다.**
판정의 목적은 절대 성립률이 아니라 **세 구현의 상대 비교**이고, 같은 입력이면 비교는 성립한다.
다만 **리포트에 "이 값은 추정"이라고 반드시 적어야** 한다 — 안 적으면 다음에 읽는 사람이
"우리 서비스 성립률은 77%"로 읽는다.

## 7. 돌리는 법

```bash
MAX_WAIT=45s docker compose up -d --build

# A — 지연·처리량
cd load-test
ARRIVAL_RATE=30 DURATION=60s TIER_DISTRIBUTION=real k6 run matching-load.js
ARRIVAL_RATE=60 DURATION=60s TIER_DISTRIBUTION=real k6 run matching-load.js

# B — 성립률 곡선
for W in 10 30 50 100 200; do
  WAITERS=$W DURATION=75s TARGET_SIZE=5 QUEUE=FLEX k6 run fill-rate-curve.js
done
for W in 10 30 50 100 200; do
  WAITERS=$W DURATION=75s TARGET_SIZE=2 QUEUE=SOLO_DUO k6 run fill-rate-curve.js
done

# C — 게이트
cd .. && python3 load-test/acceptance.py && python3 load-test/verify-invariants.py
```

각 구간 사이에 **Redis를 비운다.** 앞 구간의 확정 파티가 남으면
`busy:{userId}` 때문에 다음 구간의 후보가 줄어든다.
