# 게임 파티 자동 매칭 서비스 기능 명세서 — MVP

## 문서 범위

- 이 문서는 최초 구현 단계에서 만들 기능만 정의한다.
- 대상 게임은 **리그 오브 레전드 하나**이며 한국 서버를 기준으로 한다.
- 서비스 대상은 국내 이용자이며 모든 일정은 한국 표준시를 기준으로 한다.
- 신원은 **Discord 계정**으로 확인한다. 서비스 자체 회원가입과 비밀번호 로그인은 제공하지 않는다.
- 알림은 **서비스 화면과 브라우저 알림**으로 보낸다. Discord 다이렉트 메시지는 선택 옵션이다(8.4).
- Discord 계정은 **신원 확인**에 쓰고, 확정된 파티에는 **전용방을 만든다**(7.9).
  알림을 받기 위한 추가 설정은 요구하지 않는다.
- 일치도 점수, 조건 자동 완화, 반복 예약, 신고, 전체 이용 내역과 운영자 화면은 포함하지 않는다.
- **평가와 차단은 포함한다.** 조건 없이 만난 사람과 다시 만날 수 없으면 이 서비스는 일회용이 된다(7.7).
- 이 서비스를 왜, 누구를 위해 만드는지는 `00-prd.md`에 있다.
- 이 문서가 정의하지 않는 분산 전제·불변식·측정 기준은 `02-technical-spec-supplement.md`에 있다.

## 0. 우선순위

`P0` 없으면 핵심 흐름이 무너진다 · `P1` 완성도와 후속 단계.

| 장 | 내용 | 우선 |
|---|---|:---:|
| 1 | 신원과 기본 정보 | P0 |
| 2 | 롤 계정 연동 | P0 (2.3 스탬피드 대응만 P1) |
| 3 | 매칭 요청 생성 | P0 |
| 4 | 자동 매칭 | P0 (4.5 실패 사유 안내는 P1) |
| 5 | 즉시 매칭 제안과 수락 | P0 (5.4 재제안 억제는 P1) |
| 6 | 진행 중 요청 관리 | P0 |
| 7 | 확정 파티 관리 | P0 (7.2 준비 확인 · 7.7 평가와 재회 · 7.9 전용방은 P1) |
| 8 | 알림 | P0 (8.3 예약 리마인더 · 8.4 Discord 알림은 P1) |
| 9 | 예외 처리 | P0 |
| 10 | 자동 처리 | P0 |

**큐 우선순위는 목적에 따라 다르다**(`00-prd.md` 5.3).

- **제품 P0** — 솔로·듀오 랭크(정원 2). 격발 시점의 사용자가 실제로 취할 수 있는 행동이다.
- **검증 P0** — 자유 랭크(정원 5). 포지션 배정과 좌석 경합이 여기서만 발생한다.
- **P1** — 일반전.

### 0.1 진입 설계 제약

**요청 생성은 10초 안에 끝나야 한다.** 빡친 사람은 폼을 채우지 않는다.

- 요청마다 새로 받는 필수 입력은 **큐 · 허용 티어 범위 · 포지션 셋뿐**이다.
- 나머지 조건은 프로필 값(1.4)과 기본 포지션(2.4)을 초기값으로 채워 두고 접어 둔다.
- Riot ID는 등록해 두고 요청마다 다시 받지 않는다.
- 조건 입력 화면에 **현재 대기 인원**을 표시한다. 성립 가능성을 즉시 알아야 조건을 조정한다.

## 1. 신원과 기본 정보

### 1.1 Discord 로그인

- 서비스 이용은 Discord OAuth2 로그인으로 시작한다.
- 최초 로그인 시 Discord 계정 식별자를 서비스 계정에 연결한다.
- 요청·제안·확정 파티 상태는 계정에 귀속한다.
- 기기나 브라우저를 바꿔도 같은 Discord 계정으로 로그인하면 상태가 이어진다.

### 1.2 알림 채널

- 알림은 기본적으로 **서비스 화면과 브라우저 알림**으로 받는다(8장).
- 브라우저 알림 권한은 첫 요청을 만드는 시점에 요구하며, **거부해도 서비스를 이용할 수 있다.**
- Discord 다이렉트 메시지는 원하는 사용자만 켜는 **선택 옵션**이다(8.4).
- **어떤 알림 채널도 매칭 신청의 전제 조건이 아니다.**

> 외부 메신저 설정을 요구하는 순간 "발품 없이 지금 한 판"이라는 전제가 깨진다.
> Discord는 서버를 공유하지 않는 상대의 다이렉트 메시지를 기본 차단하는 경우가 많고,
> 그걸 풀라고 요구하면 격발 시점의 사용자는 그냥 떠난다.

### 1.3 국내 서비스 고정

- 국가·지역 선택 기능을 제공하지 않는다.
- 언어 설정과 언어 기반 매칭을 제공하지 않는다.
- 롤은 한국 서버를 기준으로 한다.
- 예약 시간은 모두 한국 표준시로 표시한다.

### 1.4 기본 프로필

- 서비스에서 사용할 닉네임을 설정한다.
- 초기값은 Discord 표시 이름을 사용하며 사용자가 변경할 수 있다.
- 음성채팅 조건을 `필수`, `가능`, `사용하지 않음` 중에서 선택한다.
- 플레이 목적을 선택한다.
  - 가볍게 즐기기
  - 승리·랭크 상승
  - 초보자 학습
  - 숙련자 중심 플레이
- 플레이 분위기를 `편안함`, `적당한 집중`, `높은 집중도` 중에서 선택한다.
- **플레이 분위기는 매칭 조건으로 사용하지 않는다.** 확정 파티 상세에만 표시한다.

> 플레이 분위기를 조건으로 쓰지 않는 이유는 플레이 목적과 의미가 겹치기 때문이다.
> 조건 축이 늘어날수록 후보가 갈려 매칭 성립률이 떨어진다.

## 2. 롤 계정 연동

### 2.1 Riot ID 등록

- `게임 이름#태그` 형식의 Riot ID를 한 번 등록한다.
- 한국 서버의 계정을 조회한다.
- 등록한 Riot ID가 본인 계정인지는 검증하지 못한다는 점을 화면에 표시한다.
- 서비스가 Riot 계정 비밀번호를 직접 입력받지 않는다.

### 2.2 조회 정보

- Riot 공식 API를 통해 다음 정보를 자동으로 가져온다.
  - 솔로·듀오 랭크 티어·단계·LP
  - 자유 랭크 티어·단계·LP
  - 승·패
  - 배치 진행 또는 언랭크 여부
- 솔로·듀오 랭크와 자유 랭크를 구분해 표시한다.
- 매칭에 필요한 요약 정보만 다른 참가자에게 공개한다.
- Riot ID 전체는 파티 확정 이후에만 공개한다.

### 2.3 연결 상태와 갱신

- 연결 상태를 `정상`, `확인 필요`, `조회 실패`로 표시한다.
- 마지막 정보 갱신 시각을 표시한다.
- 저장된 정보가 신선도 기준을 넘기면 자동으로 다시 조회한다.
- 사용자가 직접 `새로고침`을 눌러 갱신할 수 있다.
- 신선도 기준과 호출 정책은 `02-technical-spec-supplement.md` 5장에서 정의한다.

### 2.4 기본 포지션

- 프로필에 주 포지션과 부 포지션의 기본값을 설정한다.
  - 탑 / 정글 / 미드 / 바텀 / 서포터
- 주 포지션은 하나만 선택한다.
- 부 포지션은 선택하지 않거나 하나 이상 선택할 수 있다.
- `상관없음`을 선택하면 다섯 포지션 전부를 부 포지션으로 취급한다.
- 이 값은 매칭 요청 생성 시 초기값으로 채워지며, 요청마다 다르게 바꿀 수 있다.
- 매칭에 사용하는 것은 **요청에 담긴 값**이며 프로필 값이 아니다.

## 3. 매칭 요청 생성

### 3.1 즉시 매칭

- `지금 바로 플레이`를 선택한다.
- 최대 대기시간을 선택한다.
- **예상 플레이시간을 선택한다.**
- 파티가 확정되면 시작 시각은 확정 시각으로, 종료 예정 시각은 확정 시각에 예상 플레이시간을 더한 값으로 정한다.
- 대기 시작 후 현재 상태와 경과 시간을 보여준다.

> 예상 플레이시간은 화면 표시용이 아니다. 이 값이 없으면 파티에 종료 시각이 없어
> 시간이 겹치는 중복 배정(불변식 INV-2)을 판정할 수 없다.

### 3.2 일회성 예약 매칭

- 원하는 날짜와 시작 시각을 선택한다.
- 오늘 날짜의 예약은 신청할 수 없으며 다음 날 이후만 선택한다.
- 예상 플레이시간을 설정한다.
- 시작 가능 범위를 선택한다.
  - 정확한 시각
  - 앞뒤 30분 가능
  - 앞뒤 1시간 가능
- 예약 매칭은 플레이 당일 00시에 실행되며 성립한 파티는 별도의 수락 없이 자동 확정된다는 점을 신청 전에 안내한다.

### 3.3 예약 마감 경계

- 화면에 표시하는 신청·수정 마감은 **플레이 전날 23시 50분**이다.
- 실제 처리 경계는 배치 실행 시작 시각 `T`이며, `T` 이전에 생성되고 상태가 `예약됨`인 요청만 그날 배치의 대상이 된다.
- `T` 이후 도착한 신청과 수정은 해당 배치에 포함하지 않는다.
- 표시 마감과 실제 경계 사이의 10분은 안전 여유이며, 이 구간에 들어온 요청은 처리하되 보장하지 않는다.

> 표시 마감과 처리 경계를 분리하는 이유는, 마감 시각과 배치 시각이 같으면
> 경계에 걸친 요청의 처리 여부가 정의되지 않아 멱등성(불변식 INV-3)을 검증할 수 없기 때문이다.

### 3.4 큐와 인원

- 한 요청에는 큐 하나만 선택한다.
  - 솔로·듀오 랭크
  - 자유 랭크
  - 일반
- 큐별로 선택할 수 있는 목표 파티 인원이 다르다.

| 큐 | 선택 가능한 목표 인원 |
|---|---|
| 솔로·듀오 랭크 | 2 |
| 자유 랭크 | 2, 3, 5 |
| 일반 | 2, 3, 4, 5 |

- 자유 랭크는 게임 규칙상 4인 파티를 만들 수 없다.
- 혼자 신청하는 방식만 지원한다.
- 친구와 함께 신청하는 기존 파티 기능은 제공하지 않는다.

### 3.5 티어 제약

- 솔로·듀오 랭크는 게임 규칙상 함께 플레이할 수 있는 티어 범위가 제한된다.
- 제약의 형태는 티어 구간에 따라 다르다.
  - 낮은 티어 구간은 티어 단위로 여러 단계까지 허용한다.
  - 중간 티어 구간은 한 티어 위아래만 허용한다.
  - 상위 티어 구간은 티어가 아니라 **단계(디비전) 단위**로 제한한다.
- 구체적인 허용 범위는 **설정 데이터로 관리하며 코드에 고정하지 않는다.**
- 사용자는 본인 티어 기준으로 게임 규칙상 가능한 범위 안에서만 허용 티어 범위를 선택한다.
- 매칭 시 양쪽의 선택 범위를 서로 만족해야 한다.
- 자유 랭크와 일반은 이 제약을 적용하지 않는다.
- **판정에 쓰는 티어는 요청을 만든 시점에 고정한 값이다.** 요청 생성 시 조회한 티어를
  요청에 함께 저장하고, 이후 매칭은 저장된 값만 읽는다. 저장 이후 티어가 바뀌어도
  그 요청의 판정 기준은 바뀌지 않는다.

> 허용 범위를 설정으로 빼는 이유는 라이엇이 시즌마다 이 규칙을 조정하기 때문이다.
> 코드에 고정하면 규칙이 바뀔 때마다 배포해야 한다.
>
> 티어를 요청에 고정하는 이유는 다르다. 매칭이 캐시된 값을 그때그때 읽으면
> 같은 요청 집합을 다시 처리했을 때 결과가 달라진다.
> 그러면 결정적 처리(4.3)도, 배치 재실행 멱등성(불변식 INV-3)도 검증할 수 없다.

### 3.6 지원하지 않는 티어

- 한국 서버는 마스터 티어 이상 플레이어와 함께 플레이할 수 없다.
- 솔로·듀오 랭크 티어가 **마스터·그랜드마스터·챌린저**인 사용자는 솔로·듀오 랭크 요청을 만들 수 없다.
- 해당 사용자에게 사유를 표시하고 자유 랭크와 일반 큐를 안내한다.
- 자유 랭크와 일반 큐는 티어와 무관하게 이용할 수 있다.

### 3.7 언랭크와 배치 진행

- 솔로·듀오 랭크 티어가 없는 사용자(언랭크 또는 배치 진행 중)는 솔로·듀오 랭크 요청을 만들 수 없다.
- 티어를 확정하면 이용할 수 있음을 안내한다.
- 자유 랭크와 일반 큐는 티어 없이도 이용할 수 있다.
- 티어가 없는 사용자의 티어 표시는 `언랭크` 또는 `배치 중`으로 한다.

> 티어가 없으면 3.5의 허용 범위를 계산할 기준이 없다.
> 임의의 값으로 대체하면 게임에서 큐를 잡지 못하는 파티가 만들어진다.

### 3.8 매칭 조건

- 사용자가 선택한 조건은 모두 반드시 맞아야 하는 조건으로 처리한다.
- `필수 조건`과 `선호 조건`을 구분하지 않는다.
- 조건 항목은 다음과 같다.
  - 큐
  - 목표 파티 인원
  - 허용 티어 범위
  - 주·부 포지션
  - 음성채팅 여부
  - 플레이 목적
- 플레이 분위기는 조건에 포함하지 않는다.

### 3.9 신청 확인과 수정

- 신청 전 큐, 일정, 인원과 모든 조건을 한 화면에 요약한다.
- 브라우저 알림 권한이 없으면 알림을 놓칠 수 있음을 안내한다. 신청은 막지 않는다.
- 즉시 매칭 요청은 `대기 중` 상태에서만 수정하거나 취소할 수 있다.
- 일회성 예약 요청은 3.3의 마감 규칙에 따른다.
- 취소·수정 요청과 매칭 제안 생성이 동시에 일어나면 **요청 상태 전이에 먼저 성공한 쪽이 이긴다.**
  - 제안 생성이 이겼으면 취소는 실패하고, 사용자에게 제안이 도착했음을 알린 뒤 거절 경로를 제시한다.
  - 취소가 이겼으면 해당 요청은 후보에서 빠지며, 남은 인원으로 정원을 채우지 못한 제안은 생성되지 않는다.

## 4. 자동 매칭

매칭이 실행되는 시점은 두 가지다.

- **즉시 매칭**은 서버가 짧은 주기로 대기 중인 요청을 훑어 실행한다. 신청 즉시 한 번만 시도하는 것이 아니라,
  요청이 대기하는 동안 반복해서 후보를 다시 찾는다.
- **일회성 예약**은 플레이 당일 00시에 한 번 실행한다(10.1).

두 경우 모두 애플리케이션 인스턴스가 여러 대일 수 있으므로, 같은 요청이 두 파티에 동시에 묶이지 않도록
4.6의 불변식을 지켜야 한다. 실행 주기와 인스턴스 간 조정 방식은 `02-technical-spec-supplement.md` 1.4에서 정의한다.

### 4.1 후보 제외

다음 중 하나라도 해당하면 후보에서 제외한다.

- 큐가 다르다.
- 목표 파티 인원이 다르다.
- 플레이 가능한 시간이 겹치지 않는다.
- 서로의 허용 티어 범위를 양쪽 모두 만족하지 않는다.
- 게임 규칙상 함께 플레이할 수 없는 티어다(3.5).
- 음성채팅 조건이 호환되지 않는다(4.2).
- 플레이 목적이 다르다.
- 포지션을 겹치지 않게 배정할 수 없다(4.4).
- 이미 시간이 겹치는 확정 파티에 속해 있다.
- **어느 한쪽이 상대를 차단했다**(7.7). 차단은 쌍 단위로 판정하며 방향을 구분하지 않는다.

### 4.2 음성채팅 호환

- 음성채팅 조건은 `필수`, `가능`, `사용하지 않음` 세 값이며, 값이 다르다고 곧바로 제외하지 않는다.
- 두 사람 사이의 호환 여부는 다음과 같다.

| | 필수 | 가능 | 사용하지 않음 |
|---|:---:|:---:|:---:|
| **필수** | O | O | X |
| **가능** | O | O | O |
| **사용하지 않음** | X | O | O |

- 파티 전체 규칙은 다음과 같다.
  - 참가자 중 한 명이라도 `필수`이면 그 파티는 음성 파티가 되며 `사용하지 않음`인 사람을 넣지 않는다.
  - 참가자가 전부 `가능` 또는 `사용하지 않음`이면 그 파티는 비음성 파티가 된다.
- 확정된 파티의 음성 사용 여부를 파티 상세에 표시한다.

### 4.3 후보 처리 순서

- 모든 조건을 통과한 사람만 후보가 된다.
- 별도의 유사도·신뢰도 점수를 계산하지 않는다.
- 대기시간에 따라 조건을 자동으로 완화하지 않는다.
- 조건이 너무 좁으면 사용자가 요청을 직접 수정해야 한다.
- 후보 처리는 **결정적**이어야 한다. 같은 요청 집합을 입력하면 항상 같은 파티 구성이 나와야 한다.
- 처리 절차는 다음과 같다.
  1. 모든 대기 요청에 `(신청 시각, 요청 ID)` 오름차순으로 전순서를 부여한다.
  2. 아직 배정되지 않은 요청 중 순서가 가장 앞선 것을 기준 요청으로 잡는다.
  3. 기준 요청과 **이미 채택된 참가자 전원**에 대해 조건이 맞는 후보를 훑으며,
     포지션 배정이 가능한 후보만 차례로 채택한다.
     후보 순서는 **재회 목록에 있는 사람이 먼저, 그다음이 신청 순서**다(7.7).
     재회 여부는 매칭 실행 중 변하지 않는 저장된 값이므로 결정성을 깨지 않는다.
  4. 목표 인원을 채우면 파티를 성립시키고, 채우지 못하면 기준 요청을 그대로 둔 채 다음 요청으로 넘어간다.
  5. 더 이상 성립하는 파티가 없으면 종료한다.

> 순서를 `(신청 시각, 요청 ID)`로 정하는 이유는 신청 시각이 같을 때 순서가 흔들리면
> 배치 재실행 시 결과가 달라져 멱등성(불변식 INV-3)을 검증할 수 없기 때문이다.
>
> 기준 요청만이 아니라 **채택된 전원과 대조하는 이유**는 4.1의 조건 중 둘이 한 다리 건너 성립하지
> 않기 때문이다. 음성채팅 호환(4.2)과 허용 티어 범위가 그렇다. 기준 요청이 `가능`이면
> `필수`인 사람과 `사용하지 않음`인 사람이 각각 기준과는 호환이지만 **서로는 호환되지 않는다.**
> 기준하고만 대조하면 아무도 그 둘을 비교하지 않아 4.1을 위반한 파티가 성립한다.
> 포지션 배정(4.4)은 원래 참가자 전원을 한꺼번에 보므로 이 문제가 없다.

### 4.4 포지션 배정

- 한 파티 안에서 두 사람이 같은 포지션을 맡지 않는다.
- 각 참가자는 주 포지션 또는 부 포지션 중 하나를 배정받는다.
- 주 포지션을 배정받은 사람이 많을수록 좋은 배정으로 보되, 배정 가능 여부 자체는 통과·탈락 기준이다.
- 5인 파티는 탑·정글·미드·바텀·서포터를 각각 한 명씩 채운다.
- 2~4인 파티는 포지션이 서로 겹치지 않기만 하면 된다.
- 배정이 불가능한 후보 조합은 파티를 성립시키지 않는다.
- 확정된 파티의 참가자별 배정 포지션을 파티 상세에 표시한다.

### 4.5 매칭 실패 사유 안내

- 최대 대기시간이 지나 매칭에 실패하면 사유를 함께 보여준다.
- 조건을 하나씩 빼가며 각 조건이 후보를 얼마나 줄였는지 계산해 표시한다.
- 가장 많이 줄인 조건을 먼저 보여주고 수정 경로를 제시한다.
- 이 계산은 화면 표시용이며 매칭 결과에 영향을 주지 않는다.

> 조건을 자동으로 완화하지 않는 설계이므로, 왜 실패했는지 알려주지 않으면
> 사용자는 같은 조건으로 무한히 재시도하게 된다.

### 4.6 파티 구성 불변식

- 동시에 여러 매칭이 실행돼도 한 사람이 두 파티에 들어가지 않게 한다.
- 하나의 요청은 동시에 하나의 파티 구성에만 포함한다.
- 확정된 파티의 인원은 목표 인원을 넘지 않는다.
- 위 항목의 형식 정의와 검출 방법은 `02-technical-spec-supplement.md` 2장에 있다.

## 5. 즉시 매칭 제안과 수락

### 5.1 제안 도착

- 즉시 매칭에서 후보 파티가 만들어지면 참가자 전원에게 동시에 제안을 보낸다.
- 큐, 시작 시각, 인원, 배정 포지션과 일치한 조건을 보여준다.
- 상대방의 Riot ID와 Discord 계정은 확정 전까지 공개하지 않는다.
- 남은 수락 시간을 실시간으로 표시한다.

### 5.2 수락·거절

- 사용자는 제안을 수락하거나 거절한다.
- 수락 후 다른 참가자의 응답 현황을 익명으로 보여준다.
- 제한시간까지 응답하지 않으면 자동 거절로 처리한다.
- 중복 클릭이나 네트워크 재전송에도 같은 요청을 한 번만 처리한다.
- 거절한 사람이 누구인지는 다른 참가자에게 공개하지 않는다.

### 5.3 확정과 재매칭

- 즉시 매칭은 필요한 인원이 전부 수락했을 때만 파티를 확정한다.
- 한 명이라도 거절하거나 시간초과되면 해당 제안을 종료한다.
- 이미 수락했던 정상 이용자는 기존 대기 순서를 유지한 채 다시 대기한다.
- 사용자는 `계속 찾기` 또는 `매칭 종료`를 선택한다.

### 5.4 실패 조합 재제안 억제

- 조합은 참가 요청 식별자의 집합으로 정의한다.
- 실패한 조합은 실패 시각으로부터 **10분간** 다시 제안하지 않는다.
- 구성원이 한 명이라도 다르면 다른 조합으로 취급하며 억제 대상이 아니다.
- **명시적 거절로 깨진 조합만 억제한다.** 아무도 거절하지 않고 시간초과로 끝난 조합은 억제하지 않는다.

> 시간초과까지 억제하면, 알림이 늦게 닿은 참가자 한 명 때문에 정상 조합이 10분간 막힌다.
> 거절은 의사 표시지만 시간초과는 전달 실패일 수 있다.
- 억제 기록은 10분이 지나면 자동으로 사라지며 영구 보관하지 않는다.
- 억제 기록은 인스턴스가 여러 대여도 공유되어야 한다.

## 6. 진행 중 요청과 예약 관리

### 6.1 현재 요청 확인

- 로그인한 계정의 진행 중인 요청을 보여준다.
- 다음 상태를 표시한다.
  - 예약됨
  - 매칭 대기 중
  - 수락 대기 중
  - 매칭 확정
  - 재매칭 중
  - 취소됨
  - 매칭 실패
  - 이탈함
  - 완료됨
- 서버 내부 처리 단계는 사용자에게 노출하지 않는다.
- 과거에 완료된 파티 목록은 제공하지 않는다.

### 6.2 이탈 후 처리

- 확정 파티에서 스스로 나간 요청은 `이탈함` 상태로 종료한다.
- 이탈한 요청은 자동으로 다시 대기하지 않는다. 새 요청을 만들어야 한다.
- 파티가 취소되어 참가자 전원이 빠지는 경우는 `취소됨`으로 처리한다.

## 7. 확정 파티 관리

### 7.1 파티 상세

- 큐, 시작·종료 예정 시각, 참가 인원과 합의된 조건을 표시한다.
- 참가자의 서비스 닉네임, 티어 요약, 배정 포지션, 플레이 분위기를 보여준다.
- 확정 이후에만 Riot ID와 Discord 사용자명을 공개한다.
- 파티가 음성 파티인지 여부를 표시한다.
- 합류는 게임 클라이언트에서 직접 한다. 확정 이후의 연락은 파티 전용방으로 한다(7.9).
- 파티가 확정될 때 **합의된 조건(큐, 목표 인원, 플레이 목적, 음성 파티 여부)을 파티에 기록한다.**
  이후 빈자리 지원 자격 판정(7.4)과 이 화면의 표시가 모두 이 기록을 기준으로 한다.

### 7.2 준비 확인

- 시작 전에 `참여 가능`, `늦을 예정`, `참여 불가` 중 하나를 선택한다.
- 아직 응답하지 않은 인원 수를 보여준다.
- 예약 파티는 이 시점에 참가자 티어를 다시 조회해, 게임 규칙상 함께 큐를 잡을 수 있는지 재검증한다.
  불가능해졌으면 참가자에게 알린다. 파티를 자동으로 해체하지는 않는다.

> 예약 파티는 확정과 플레이 사이가 최대 21시간 벌어진다(당일 00시 확정, 그날 저녁 플레이).
> 그사이 승급하면 3.5의 제약을 넘겨 게임에서 큐를 잡지 못하는 파티가 된다.
> 재검증 결과는 안내용이며 매칭 판정에 쓰지 않는다. 판정 기준은 3.5의 고정된 값이다.

### 7.3 확정 후 이탈

- 확정된 파티에서 나갈 수 있다.
- 이탈 사유와 시각을 기록한다.
- 시작 직전 이탈에는 경고를 보여준다.
- 이탈을 처리한 직후 남은 인원을 판정한다.
  - 남은 인원이 **2명 미만**이면 파티 전체를 취소하고 참가자에게 알린다.
  - 남은 인원이 2명 이상이면 파티를 유지하고 빈자리를 공개 모집으로 전환한다(7.4).
- 여러 명이 동시에 이탈해도 각 이탈 처리마다 순차적으로 판정한다.

### 7.4 빈자리 공개 모집

- 이탈로 생긴 빈자리는 **비어 있는 포지션 단위의 좌석**으로 공개한다.
- 조건이 맞는 대기 중인 사용자에게 모집 중인 좌석 목록을 보여준다.
- 지원 자격은 **지원자와 기존 참가자 전원** 사이에서 판정하며, 기준은 다음과 같다.
  - 큐와 목표 인원이 파티와 같다.
  - 지원자가 그 좌석의 포지션을 주 또는 부 포지션으로 맡을 수 있다.
  - 기존 참가자 전원과 티어 조건을 서로 만족한다.
  - 파티가 음성 파티이면 지원자의 음성채팅 조건이 `사용하지 않음`이 아니다.
  - 플레이 목적이 파티의 합의된 목적과 같다.
  - 시간이 겹치는 확정 파티에 속해 있지 않다.
- 지원은 **선착순으로 즉시 확정**하며 기존 참가자의 수락 절차를 거치지 않는다.
- 좌석이 채워지면 즉시 마감하고, 이후 도착한 지원은 실패로 응답한다.
- **여러 명이 같은 좌석에 동시에 지원해도 정원을 넘겨 확정하지 않는다.**
- 좌석이 채워지면 기존 참가자에게 새 참가자를 알린다.

> 이 절이 정원 초과(불변식 INV-1)를 만드는 유일한 경로다.
> 전원 수락으로만 확정하는 5장 경로에서는 좌석을 놓고 경쟁하는 사람이 없어 경합이 발생하지 않는다.

### 7.5 모집 마감과 인원 확정

- 모집 마감 시각은 파티 종류에 따라 다르다.
  - **예약 파티**는 시작 예정 시각 **10분 전**에 마감한다.
  - **즉시 매칭 파티**는 **모집 시작 시점부터 15분간** 열어 두고 마감한다.
- 마감 시점의 인원으로 파티를 확정하되, 다음 경우에는 파티를 취소한다.
  - 인원이 2명 미만이다.
  - 인원이 해당 큐에서 허용되지 않는 수다.
- 자유 랭크는 4인 파티를 만들 수 없으므로, 5인 자유 랭크 파티가 4인으로 마감되면 취소한다.
- 목표 인원에 못 미치지만 큐 규칙상 허용되는 인원이면 그대로 진행하고, 줄어든 인원과 빈 포지션을 참가자에게 알린다.

> 즉시 매칭 파티의 시작 시각은 확정 시각이다(3.1). 예약 파티와 같은 규칙(시작 10분 전 마감)을 쓰면
> 모집 창이 **열리자마자 닫혀** 빈자리 충원이 성립하지 않는다.
> 정원 초과(불변식 INV-1)는 이 경로에서만 발생하므로, 그 경우 재현할 위반 자체가 사라진다.

### 7.6 완료 처리

- 완료 전환은 **이벤트로 한다.** 참가자 중 한 명이 `플레이 종료`를 누르면 그 시점에 완료로 전환한다.
- 종료 예정 시각(3.1)은 **백스톱**으로만 쓴다. 예정 시각에서 일정 시간이 더 지나도 아무 이벤트가
  없으면 그때 자동으로 완료 처리한다.
- 완료 전환 시 참가자에게 평가를 요청한다(7.7).

> 게임은 시계로 끝나지 않는다. 예상 플레이시간을 그대로 종료 시각으로 쓰면
> 롱게임이 진행 중인데 파티가 완료 처리된다.
> 예상 플레이시간의 역할은 세 가지뿐이다 — 매칭 조건, 시간 겹침 판정(불변식 INV-2), 리소스 정리 시점.

### 7.7 평가와 재회

- 파티가 완료되면 함께한 참가자를 **`또 하고 싶다` / `아니다`** 중 하나로 평가한다.
- 평가는 **1클릭**으로 끝난다. 사유를 입력받지 않는다.
- 평가하지 않고 넘어갈 수 있다. 평가를 강제하지 않는다.
- 평가 결과는 **상대에게 공개하지 않는다.**
- `또 하고 싶다`로 평가한 사람은 **재회 목록**에 남는다.
  - 재회 목록의 사람과는 다음 요청에서 우선 매칭을 시도한다.
  - 상대도 나를 `또 하고 싶다`로 평가했는지는 조건에 넣지 않는다. 한쪽 평가만으로 목록에 넣는다.
- `아니다`로 평가한 사람은 **차단 쌍**이 되어 이후 서로의 후보에서 제외된다(4.1).
- 차단은 해제할 수 있다.
- 신고와 사유 수집, 내부 신뢰도 점수는 만들지 않는다.

> 평가와 재회를 넣는 이유는 친목이 아니다. 조건만으로 만난 사람은 게임이 끝나면
> 서로의 연락처를 교환하고 이 서비스를 떠난다. 그러면 이 서비스는 **일회용**이 된다.
> 재회 목록은 사용자가 다시 돌아올 유일한 이유다.
>
> 우선 매칭은 조건을 완화하지 않는다. **조건을 전부 통과한 후보 안에서 순서만 앞당긴다.**
> 조건 자동 완화를 하지 않는다는 4.3의 원칙은 그대로다.

### 7.8 재회 목록

- 재회 목록에 남는 정보는 **서비스 닉네임과 마지막으로 함께한 시각**뿐이다.
- 과거 파티의 상세 내역, 전적, 대화는 저장하지 않는다.
- 사용자가 목록에서 직접 지울 수 있다.
- 목록은 계정에 귀속하며 기기를 바꿔도 이어진다.

> 전체 이용 내역을 남기지 않는다는 문서 범위의 원칙은 유지한다.
> 재회에 필요한 최소 정보만 남긴다.

### 7.9 Discord 전용방

- 파티가 확정되면 **서비스 Discord 서버에 그 파티 전용 비공개 텍스트 채널을 자동으로 만들고,
  참가자 전원을 그 채널에 넣는다.**
- 채널은 해당 파티의 참가자만 읽고 쓸 수 있다.
- **투입도 자동이다.** 사용자가 초대 링크를 누르거나 채널을 찾아 들어가는 절차를 요구하지 않는다.
- 빈자리가 충원되면 새 참가자를 같은 채널에 넣는다(7.4).
- 이탈한 참가자는 채널에서 내보낸다(7.3).
- 파티 상세에 채널 입장 경로를 표시한다.
- 서버에 가입하지 않은 참가자는 채널에 넣을 수 없다. 초대 경로를 안내하고, 가입하면 그 시점에 넣는다.
- **서버 가입은 매칭 신청과 파티 확정의 전제 조건이 아니다.** 가입하지 않은 참가자가 있어도
  파티는 그대로 성립하며, 그 사람만 채널에 들어오지 못한다.
- 채널 생성이나 참가자 투입이 실패해도 파티는 유지한다. 실패 사실만 표시하고 파티를 해체하지 않는다(9.1).
- 넣을 대상이 하나도 없으면 채널을 만들지 않는다. 이 경우는 실패와 구분해 기록한다.
- **음성 채널은 만들지 않으며, 사용자를 음성방에 접속시키지 않는다.**
- 채널의 대화 내용은 서비스가 저장하지 않는다.
- 채널은 파티가 완료되거나 취소된 뒤 정리한다(10.5).

> 합류 자체는 게임 클라이언트에서 한다. 전용방이 있는 이유는 합류가 아니라
> **확정 이후의 연락 수단**이다. "10분 늦는다" 한마디를 전할 곳이 없으면 참가자들은
> 서로 Discord 친구를 추가하고 이 서비스를 떠난다. 7.7과 같은 이유다.
>
> 참가자가 직접 들어가게 하지 않고 넣어주는 이유도 같다. 초대 링크를 누르는 절차를 요구하면
> 다섯 명 중 한둘은 안 누르고, 그러면 전용방은 연락 수단으로 기능하지 못한다.
>
> 그래서 전용방은 **있으면 좋은 것**으로 두고 전제 조건으로 만들지 않는다.
> 서버 가입을 확정의 조건으로 걸면 "발품 없이 지금 한 판"이라는 1.2의 전제가 깨진다.
> 전용방이 없어도 파티는 게임 클라이언트에서 성립한다.

## 8. 알림

알림은 **우리 서비스 화면과 브라우저 알림으로 보낸다.** 외부 메신저를 요구하지 않는다.

| 채널 | 언제 쓰는가 | 우선 |
|---|---|:---:|
| 인앱 실시간 (8.1) | 서비스 화면이 열려 있을 때 — **1차 채널** | P0 |
| 웹 알림 (8.2) | 화면을 닫았거나 다른 창을 보고 있을 때 — **보조 채널** | P0 |

### 8.1 인앱 실시간 상태

- 새로고침 없이 대기·제안·수락·확정 상태를 갱신한다.
- 연결이 끊기면 자동 재연결한다.
- 재연결 후 현재 상태를 다시 불러온다.
- 참가자가 서로 다른 애플리케이션 인스턴스에 붙어 있어도 같은 시점에 전달한다.
- 화면이 열려 있으면 이 채널만으로 모든 알림이 전달된다.
- 탭이 백그라운드에 있으면 **탭 제목과 파비콘으로 대기 중인 알림 수를 표시한다.**

### 8.2 웹 알림

- 브라우저 알림(Web Push)으로 다음을 알린다.
  - 즉시 매칭 제안 도착
  - 수락 제한시간 임박
  - 매칭 확정
  - 빈자리 충원 완료
  - 인원 감소로 인한 변경
  - 파티 취소
  - 시작 전 준비 확인
  - 플레이 종료 후 평가 요청
- 알림을 누르면 해당 요청·파티 화면으로 바로 이동한다.
- 권한은 **첫 요청을 만드는 시점에** 요구한다. 첫 방문에 바로 묻지 않는다.
- **권한을 거부해도 서비스를 이용할 수 있다.** 알림을 놓칠 수 있다는 점만 안내한다.
- 전송에 실패하면 인앱 상태로만 안내하고 실패를 기록한다.
- 같은 알림을 두 번 보내지 않는다.

> 이 서비스는 PC에서 롤을 하다가 여는 서비스다. 데스크톱 브라우저는 웹 알림을 완전히 지원하고,
> 브라우저가 떠 있으면 탭을 닫아도 알림이 도착한다. 방금 브라우저에서 요청을 넣은 사용자라면
> 브라우저는 켜져 있다.
>
> 모바일 브라우저, 특히 iOS는 홈 화면에 추가하지 않으면 웹 알림을 받지 못한다.
> **모바일에서는 예약 알림이 전달되지 않을 수 있음을 안내한다.** 이 한계를 감수하는 대신
> 외부 메신저 가입·설정을 요구하지 않는다.

### 8.3 예약 리마인더

- 파티 시작 24시간 전, 1시간 전, 10분 전에 8.1·8.2 채널로 알린다.
- 이미 취소된 파티에는 알림을 보내지 않는다.
- 파티가 취소되면 아직 발송되지 않은 알림을 회수한다.
### 8.4 Discord 알림 (선택)

- 사용자가 원하면 Discord 다이렉트 메시지로도 같은 알림을 받을 수 있다.
- **기본값은 꺼짐이다.** 켜지 않아도 모든 기능을 쓸 수 있다.
- 켜려면 Discord Bot의 다이렉트 메시지를 받을 수 있어야 하며, 방법을 안내한다.
- 수신할 수 없는 상태이면 그 사실만 표시하고 **매칭 신청을 막지 않는다.**


## 9. 예외 처리

### 9.1 외부 정보 오류

- Riot ID 형식 오류, 존재하지 않는 계정, 언랭크와 API 장애를 구분한다.
- 브라우저 알림 권한 거부, 구독 만료와 푸시 서비스 장애를 구분한다.
- Discord 알림을 켠 사용자에 한해 권한 거절·다이렉트 메시지 차단·Bot 장애를 구분한다.
- 전용방 생성과 참가자 투입 실패는 **Bot 권한 부족·참가자의 서버 미가입·Discord 장애**를 구분한다(7.9).
- 일부 참가자만 투입에 실패한 경우와 채널 자체를 만들지 못한 경우를 구분한다.
- 기존 조회 정보가 있으면 마지막 갱신 시각을 함께 표시한다.
- Riot API 장애 중에는 저장된 정보로 매칭을 계속하되 갱신 실패를 표시한다.

### 9.2 매칭 오류

- 시간이 겹치는 요청을 중복 생성하지 못하게 한다.
- 여러 사용자가 동시에 응답하거나 지원해도 파티 정원을 초과하지 않게 한다.
- 만료된 제안에 응답하면 최신 상태를 다시 보여준다.
- 이미 마감된 좌석에 지원하면 마감 사실을 알리고 목록을 갱신한다.
- 다시 접속하면 현재 진행 상태를 복구한다.

### 9.3 시간 오류

- 이미 지난 시각으로 예약하지 못하게 한다.
- 오늘 날짜의 일회성 예약은 신청하지 못하게 한다.
- 3.3의 마감을 지난 예약은 새로 만들거나 수정하지 못하게 한다.

## 10. 자동 처리

### 10.1 일회성 예약 매칭 배치

- 매일 00시 한국 표준시를 기준으로 당일 일회성 예약 매칭을 한 번 실행한다.
- 3.3의 경계 규칙에 따라 대상 요청을 결정한다.
- 4.3의 결정적 절차로 파티를 구성한다.
- 매칭된 파티는 별도의 수락 절차 없이 자동 확정한다.
- 파티를 구성하지 못한 예약은 매칭 실패로 종료한다.
- 미래 날짜의 예약은 해당 플레이 날짜 00시가 될 때까지 처리하지 않는다.
- 작업 장애로 배치가 재실행되거나 두 인스턴스에서 동시에 실행되더라도 사용자가 여러 파티에 중복 배정되지 않게 한다.

### 10.2 즉시 매칭 만료

- 최대 대기시간이 지나면 즉시 매칭 요청을 자동 종료한다.
- 종료 시 4.5의 실패 사유를 함께 제공한다.
- 수락 제한시간이 지나면 해당 즉시 매칭 제안을 자동 거절 처리한다.

### 10.3 외부 정보 동기화

- Riot 정보의 갱신 주기를 관리한다.
- 신선도 기준 안의 정보는 다시 호출하지 않고 저장된 값을 사용한다.
- 동일 계정에 대한 동시 조회를 하나로 합친다.
- 외부 API 호출 제한과 일시 장애에 대응한다.

### 10.4 알림 작업

- 파티 확정 시 예약 리마인더 작업을 생성한다.
- 파티 취소 시 남은 알림 작업을 회수한다.
- 동일한 알림을 중복 발송하지 않는다.

### 10.5 전용방 정리

- 파티 확정 시 전용방 생성 작업을 만든다(7.9).
- 좌석이 충원되거나 참가자가 이탈하면 채널 구성원을 갱신한다(7.9).
- 파티가 완료되거나 취소되면 전용방 삭제를 예약한다. 완료·취소 즉시 지우지 않는다.
- 삭제 예정 시각은 **완료·취소 시각으로부터 24시간 뒤**로 둔다.
- 생성·투입·삭제 명령이 중복 전달돼도 채널을 두 번 만들거나 같은 사람을 두 번 넣지 않는다.

> 즉시 지우지 않는 이유는 완료 전환이 이벤트이기 때문이다(7.6).
> 한 명이 `플레이 종료`를 누른 시점에 다른 참가자는 아직 채널에서 이야기하고 있을 수 있다.

## 11. MVP 완료 기준

- [ ] Discord 계정으로 로그인하고 기기를 바꿔도 상태가 이어진다.
- [ ] 알림 채널 없이도 매칭을 신청할 수 있고, 권한 거부 시 한계를 안내할 수 있다.
- [ ] Riot ID를 등록하고 티어 정보를 자동으로 가져올 수 있다.
- [ ] 티어에 따라 선택 가능한 큐와 허용 티어 범위를 제한할 수 있다.
- [ ] 즉시 매칭과 일회성 예약을 만들 수 있다.
- [ ] 매일 00시에 당일 일회성 예약을 매칭하고 성립한 파티를 자동 확정할 수 있다.
- [ ] 요청 생성 시점의 티어를 고정해, 같은 요청 집합에 항상 같은 매칭 결과를 낼 수 있다.
- [ ] 조건이 일치하는 사람을 결정적 순서로 구성할 수 있다.
- [ ] 5인 파티를 포지션이 겹치지 않게 배정할 수 있다.
- [ ] 매칭 실패 시 어느 조건이 후보를 가장 많이 줄였는지 보여줄 수 있다.
- [ ] 동시에 매칭해도 사용자가 중복 배정되지 않는다.
- [ ] 즉시 매칭 제안과 전원 수락을 처리할 수 있다.
- [ ] 실패한 즉시 매칭 제안의 정상 이용자를 재대기시킬 수 있다.
- [ ] 확정 파티의 준비 확인과 이탈을 관리할 수 있다.
- [ ] 플레이 종료 이벤트로 파티를 완료 전환하고, 예정 시각은 백스톱으로만 쓴다.
- [ ] 완료 후 1클릭 평가를 받고, 재회 목록과 차단 쌍을 매칭에 반영할 수 있다.
- [ ] 이탈로 생긴 빈자리를 공개 모집하고, 동시 지원에도 정원을 초과하지 않는다.
- [ ] 모집 마감 시 큐 규칙상 불가능한 인원이면 파티를 취소할 수 있다.
- [ ] 확정 파티에 전용방을 만들고 참가자 전원을 넣으며, 명령이 중복 전달돼도 채널을 하나만 만든다.
- [ ] 서로 다른 인스턴스에 붙은 참가자 전원에게 제안을 동시에 전달할 수 있다.
- [ ] 화면을 닫은 사용자에게 브라우저 알림으로 제안·확정·리마인더를 전달할 수 있다.
- [ ] 알림을 예약·회수하고 중복 발송하지 않는다.
- [ ] 만료 처리와 알림 정리를 자동으로 수행한다.

## 12. MVP에서 제외하는 기능

- PUBG와 Steam 게임 지원
- Riot Sign On을 통한 계정 소유 검증
- MMR 기반 추가 제한의 재현 — Riot API로 조회할 수 없다
- 마스터 이상 티어의 솔로·듀오 랭크 매칭
- 일치도 점수와 조건 자동 완화
- 반복 예약
- 신고와 내부 신뢰도 점수 (평가·차단·재회는 7.7에 포함한다)
- 전체 이용 내역과 매칭 템플릿 (재회 목록은 7.8에 포함한다)
- 운영자 관리 화면
- 자체 음성통화·영상통화
- 사용자 간 금전 거래
- 자유 게시판 중심의 커뮤니티
- 게임 계정 비밀번호 직접 수집
- 사용자를 Discord 음성방에 강제로 접속시키는 기능
