# 기술 보완 명세

기능 명세서(`01-functional-spec-mvp.md`)가 "무엇을 만드는가"를 정의한다면,
이 문서는 **"무엇이 깨지면 실패로 보는가"**를 정의한다.

- 1장 — 분산 전제. 왜 인스턴스 2대인가, 상태를 어디에 두는가, 무엇이 매칭을 돌리는가.
- 2장 — 불변식과 위반 검출. 통과 게이트의 형식 정의와 강제 수단.
- 3장 — 실시간 전달. 제안 팬아웃과 인스턴스 간 전파.
- 4장 — 알림. 지연 큐, 회수, 중복 차단.
- 5장 — 외부 API. 신선도, 호출 병합, 레이트리밋.
- 6장 — 측정. 부하 프로파일, 입력 분포, 목표 수치가 유효한 조건.

---

## 1. 분산 전제

### 1.1 구성

```
                      ┌──────────┐
                  ┌──▶│  App #1  │──┐
   부하        ┌──┴─┐ └──────────┘  │   ┌─────────┐
   발생기 ────▶│ LB │               ├──▶│   RDB   │  파티 · 요청 · 배정 (권위 있는 상태)
               └──┬─┘ ┌──────────┐  │   └─────────┘
                  └──▶│  App #2  │──┤
                      └──────────┘  │   ┌─────────┐
                                    └──▶│  Redis  │  분산 락 · Pub/Sub · 지연 큐 · 캐시
                                        └─────────┘
```

**LB가 그림에 있어야 하는 이유.** 요청을 두 인스턴스에 나누는 주체가 없으면
경합이 왜 생기는지 설명되지 않는다. 그리고 SSE 연결은 **한 인스턴스에 고정된다.**
같은 사용자의 API 요청이 다른 인스턴스로 갈 수 있다는 사실이
제안 전파에 Pub/Sub이 필요한 직접적인 이유다(3장).

### 1.2 왜 인스턴스가 둘 이상이어야 하는가

- 인스턴스가 하나면 애플리케이션 내부 락만으로 좌석 경합과 중복 배정이 막힌다.
- 막히면 문제가 재현되지 않고, 재현되지 않으면 데이터베이스 제약과 분산 락의 필요성을 증명할 수 없다.
- 제안 팬아웃(INV 밖의 기능 요구)과 배치 중복 실행은 인스턴스가 둘 이상일 때만 나타난다.
- 따라서 **모든 측정은 인스턴스 2대 이상에서 수행한다.** 1대 측정값은 비교군으로도 쓰지 않는다.

### 1.3 상태의 소재

| 상태 | 위치 | 이유 |
|---|---|---|
| 파티, 참가자, 요청, 배정 포지션 | RDB | 불변식 검증의 유일한 권위. 위반 계수는 여기서만 센다. |
| 분산 락 | Redis | 배치 단일 실행, 좌석 경합 제어 비교군 |
| 제안 전파 | Redis Pub/Sub | 인스턴스 간 팬아웃 |
| 알림 예약 | Redis Sorted Set | 지연 큐. 회수 가능해야 함 |
| Riot 조회 결과 | Redis | 신선도 기준 안에서 재사용 |

- **캐시는 권위가 아니다.** Redis가 통째로 날아가도 불변식은 깨지지 않아야 한다.
- 캐시 소실 후 재기동을 측정 시나리오에 포함한다(5.3 스탬피드).

> 이 주장은 조건부다. 분산 락이 Redis에 있으므로 **락이 사라지면 두 인스턴스가 배치에 동시 진입한다.**
> 그때도 INV-3이 유지되는 것은 `party_member.request_id` 유니크 제약이 PostgreSQL에 있기 때문이다.
> 제약 없이 락에만 기대면 이 문장은 성립하지 않는다.
> **락은 최적화이고, 정합성은 제약이 보장한다.**

### 1.4 즉시 매칭 실행기

예약 매칭은 실행 시점이 정해져 있지만(매일 00시), 즉시 매칭은 그렇지 않다.
**누가 언제 매칭을 돌리는지**가 정해져야 무엇이 경합하는지도 정해진다.

- 각 인스턴스가 주기적으로 대기 요청을 훑는 **틱 루프**를 돈다.
- 두 인스턴스가 같은 대기 풀을 자유롭게 훑으면 그 자체가 경합이 된다.
  같은 후보로 서로 다른 파티를 만들 수 있기 때문이다.
- 이 경합은 INV-3(요청 단일 배정)이 흡수한다. 한 요청이 두 파티에 들어가려 하면
  유니크 제약이 두 번째 삽입을 막고, 진 쪽의 파티 구성은 폐기된다.
- 2단계에서 비교하는 **파티션 단일 라이터** 전략은 여기에도 적용된다.
  큐 단위로 실행기를 나누면 애초에 겹치지 않는다. 처리량·지연·구현 복잡도로 함께 잰다.

> 실행 주기는 측정으로 정한다. 짧으면 빈 조회가 늘고, 길면 대기 시간이 늘어난다.
> 초기값은 1초로 두고 매칭 성립률 곡선(6.3)과 함께 조정한다.

### 1.5 시계

- 만료·마감·배치 기준 시각은 **애플리케이션 시계가 아니라 데이터베이스 시계**를 사용한다.
- 인스턴스 간 시계 차이가 제안 만료와 좌석 마감의 판정을 갈라놓으면 안 된다.
- 지연 측정(6.2)만은 단일 시계 기준으로 별도 수집한다.

## 2. 불변식과 위반 검출

**위반 검출은 로그가 아니라 데이터베이스를 직접 검사해서 계수한다.**
위반이 발생했는데 로그에 안 남는 경우가 가장 위험하기 때문이다.

각 불변식은 아래 검사 질의가 **0행을 반환해야** 통과한다. 1행이라도 나오면 탈락이다.

### 참조 스키마 (검출에 필요한 최소 형태)

```
match_request(id, user_id, queue, target_size, status, requested_at, play_minutes,
              tier_snapshot, tier_snapshot_at, purpose, voice_mode, ...)
party(id, queue, target_size, start_at, end_at, status, purpose, voice_party)
party_member(party_id, request_id, user_id, position, joined_at,
             left_at, leave_reason)
user_busy_interval(user_id, during, party_id)
party_rating(party_id, rater_id, ratee_id, verdict, rated_at)
user_relation(user_id, other_id, kind, updated_at)   -- kind: REUNION | BLOCK
notification_job(id, party_id, user_id, kind, fire_at, status, dedup_key)
```

세 가지가 검출을 위해 반드시 필요하다.

- **`match_request.tier_snapshot`** — 매칭에 쓰는 티어는 캐시가 아니라 요청에 고정된 값이다.
  캐시된 값을 읽으면 배치를 두 번 돌릴 때 티어가 갱신돼 결과가 달라지고,
  결정적 FCFS(기능 명세 4.3)와 INV-3 검증이 동시에 무너진다.
- **`party_member.left_at`** — 이탈 사유·시각을 기록하면서(기능 명세 7.3)
  이탈자가 정원 계수에 포함되지 않게 하려면 상태가 필요하다.
  **INV-1·INV-4 질의는 반드시 `left_at IS NULL`로 걸러야 한다.**
- **`user_busy_interval`** — INV-2를 데이터베이스 제약으로 막으려면
  사용자와 시간 구간이 **한 테이블 안에** 있어야 한다(INV-2 항 참조).

`party.purpose`·`party.voice_party`는 빈자리 지원 자격 판정(기능 명세 7.4)이
"파티의 합의된 목적"과 "파티가 음성 파티인지"를 요구하기 때문에 필요하다.

`user_relation`은 재회·차단(기능 명세 7.7)을 담는다. 매칭 실행 중에는 읽기만 하므로
**결정적 FCFS의 입력 불변성을 깨지 않는다.** 평가는 파티 완료 후에만 쓰이고,
진행 중인 매칭의 후보 순서를 실행 도중 바꾸지 않는다.
`(rater_id, ratee_id, party_id)`에 유니크 제약을 걸어 중복 평가를 막는다.

### INV-1 — 정원 초과 (문제 1)

확정된 파티의 인원은 목표 인원을 넘지 않는다.

```sql
SELECT p.id, p.target_size, COUNT(pm.request_id) AS actual
FROM party p
JOIN party_member pm ON pm.party_id = p.id
WHERE p.status IN ('CONFIRMED', 'RECRUITING')
  AND pm.left_at IS NULL
GROUP BY p.id, p.target_size
HAVING COUNT(pm.request_id) > p.target_size;
```

- 이 위반은 **7.4 빈자리 공개 모집 경로에서만** 발생한다.
- 전원 수락 확정 경로에는 좌석을 놓고 경쟁하는 사람이 없어 경합이 생기지 않는다.
- 1단계는 이 경로를 제어 없이 구현해 위반을 **재현하는 것이 목표**다. 재현되지 않으면 2단계로 넘어가지 않는다.
- **재현은 예약 파티로만 가능하다.** 즉시 매칭 파티는 확정 시각이 곧 시작 시각이라
  모집 창이 열리자마자 닫힌다(기능 명세 7.5). 부하 시나리오를 즉시 매칭으로 짜면
  위반이 한 건도 나오지 않고, 그것을 "제어가 잘 됐다"로 오독하게 된다.
- INV-1은 다섯 불변식 중 **유일하게 단순 제약으로 막을 수 없다.** 정원은 행 하나가 아니라
  집합의 크기이기 때문이다. 이 프로젝트가 문제 1을 핵심으로 잡은 이유가 여기에 있다.

### INV-2 — 시간이 겹치는 중복 배정 (문제 2)

한 사람이 시간이 겹치는 두 파티에 동시에 속하지 않는다.

```sql
SELECT a.user_id, a.party_id, b.party_id
FROM party_member a
JOIN party_member b
  ON a.user_id = b.user_id
 AND a.party_id < b.party_id
JOIN party pa ON pa.id = a.party_id
JOIN party pb ON pb.id = b.party_id
WHERE pa.status IN ('CONFIRMED', 'RECRUITING')
  AND pb.status IN ('CONFIRMED', 'RECRUITING')
  AND tstzrange(pa.start_at, pa.end_at) && tstzrange(pb.start_at, pb.end_at);
```

- 이 질의가 성립하려면 **모든 파티에 `end_at`이 있어야 한다.**
  즉시 매칭에 예상 플레이시간을 받는 이유가 이것이다(기능 명세 3.1).
- 3단계에서 제약을 애플리케이션에 둘지 데이터베이스에 둘지 결정한다.

**데이터베이스에 둘 경우 — 별도 테이블이 필요하다.**

배제 제약은 **한 테이블 안의 컬럼끼리만** 성립한다. `user_id`는 `party_member`에,
`start_at`·`end_at`은 `party`에 있으므로 두 테이블에 걸친 배제 제약은 만들 수 없다.
사용자의 점유 구간을 한 행으로 모은 테이블을 두고 거기에 건다.

```sql
CREATE TABLE user_busy_interval (
  user_id  BIGINT      NOT NULL,
  during   TSTZRANGE   NOT NULL,
  party_id BIGINT      NOT NULL,
  EXCLUDE USING gist (user_id WITH =, during WITH &&)
);
```

- 파티 확정·좌석 충원 시 행을 넣고, 이탈·취소 시 지운다. 파티 상태 필터가 행 존재 여부로 대체된다.
- 제약 위반이 애플리케이션 예외로 어떻게 드러나는지(`23P01 exclusion_violation`)도 함께 기록한다.
- 애플리케이션 검증과 비교할 때, **사전 검증은 경합 조건에서 누락이 발생하고
  배제 제약은 발생하지 않는다**는 것을 검출 질의로 보여야 한다.

### INV-3 — 요청 단일 배정 (문제 3)

하나의 요청은 최대 하나의 파티에만 속한다. 배치가 재실행돼도 마찬가지다.

```sql
SELECT request_id, COUNT(*) AS assigned_count
FROM party_member
GROUP BY request_id
HAVING COUNT(*) > 1;
```

**이 불변식은 제약으로 강제한다.**

```sql
ALTER TABLE party_member ADD CONSTRAINT uq_member_request UNIQUE (request_id);
```

- 유니크 제약이 있으면 **배치는 구조적으로 멱등해진다.** 재실행이 같은 요청을 다시 넣으려 하면
  삽입이 실패하고, 그 실패를 정상 흐름으로 처리하면 된다. 락이 아니라 쓰기 자체가 멱등성을 보장한다.
- 이탈한 요청은 재대기하지 않으므로(기능 명세 6.2) 한 요청은 평생 최대 한 파티에 속한다.
  이 제약이 성립하는 전제이며, 재대기를 허용하도록 명세를 바꾸면 제약도 함께 바뀌어야 한다.
- **제안 단계에서는 `party_member`를 쓰지 않는다.** 제안이 실패하면 참가자는 다시 대기하는데
  (기능 명세 5.3), 제안 시점에 행을 만들면 재대기 후 두 번째 행이 생겨 이 제약에 걸린다.
  행은 **확정 시점에만** 만든다.
- 검출 질의의 역할은 위반을 찾는 것이 아니라 **제약이 실제로 걸려 있고 동작하는지 확인**하는 것이다.

- 배치 멱등성 시나리오는 세 가지를 모두 돌린다.
  1. 배치를 순차로 두 번 실행
  2. 두 인스턴스에서 동시에 실행
  3. 첫 실행이 파티를 일부 만든 상태에서 강제 종료 후 재실행
- 4단계에서 **락 만료 중 작업이 계속되는 경우**를 별도로 다룬다.
  분산 락 TTL이 배치 소요시간보다 짧으면 락이 풀린 뒤에도 첫 실행이 쓰기를 계속한다.
  이때 멱등성은 락이 아니라 쓰기 자체의 조건부 성립으로 보장해야 한다.

### INV-4 — 포지션 중복 (문제 7)

한 파티 안에서 두 사람이 같은 포지션을 맡지 않는다.

```sql
SELECT party_id, position, COUNT(*) AS dup
FROM party_member
WHERE left_at IS NULL
GROUP BY party_id, position
HAVING COUNT(*) > 1;
```

**이 불변식도 제약으로 강제한다.** 이탈한 자리는 다시 열려야 하므로 부분 유니크 인덱스를 쓴다.

```sql
CREATE UNIQUE INDEX uq_member_position
  ON party_member (party_id, position) WHERE left_at IS NULL;
```

- 빈자리 공개 모집(기능 명세 7.4)이 **포지션 단위 좌석**인 이유가 이것이다.
  좌석 하나 = 이 인덱스의 키 하나이며, 동시 지원자 중 하나만 삽입에 성공한다.

### INV-5 — 알림 중복 발송 (문제 5)

같은 알림을 두 번 보내지 않는다.

```sql
SELECT dedup_key, COUNT(*) AS sent
FROM notification_job
WHERE status = 'SENT'
GROUP BY dedup_key
HAVING COUNT(*) > 1;
```

- 취소된 파티에 알림이 남아 있는 경우도 함께 검사한다.

```sql
SELECT n.id
FROM notification_job n
JOIN party p ON p.id = n.party_id
WHERE p.status = 'CANCELLED'
  AND n.status = 'SCHEDULED';
```

### 게이트 요약

| 불변식 | 대응 문제 | 강제 수단 | 판정 |
|---|:---:|---|---|
| INV-1 정원 초과 | 1 | **없음 — 제어 전략을 비교하는 대상** | 0건 |
| INV-2 시간 겹침 중복 배정 | 2 | 배제 제약 vs 애플리케이션 검증 (3단계에서 결정) | 0건 |
| INV-3 요청 단일 배정 | 3 | `UNIQUE (request_id)` | 0건 |
| INV-4 포지션 중복 | 7 | `UNIQUE (party_id, position) WHERE left_at IS NULL` | 0건 |
| INV-5 알림 중복 발송 | 5 | `UNIQUE (dedup_key)` | 0건 |

다섯 중 넷은 제약으로 막을 수 있고, **INV-1만 막을 수 없다.**
정원은 행 하나의 속성이 아니라 집합의 크기이기 때문이다.
그래서 1·2단계가 이 프로젝트의 본체다.

검출 질의는 전부 RDB에서 실행한다. 제약이 있는 넷에 대해서는
"위반을 찾는 장치"가 아니라 **"제약이 실제로 걸려 있고 동작하는지 확인하는 장치"**로 쓴다.

---

## 3. 실시간 전달

### 3.1 요구

- 제안 1건은 참가자 전원에게 **같은 시점에** 도착해야 한다.
- 참가자들은 서로 다른 애플리케이션 인스턴스에 붙어 있다.
- 먼저 받은 사람이 유리해지면 안 된다. 수락 제한시간은 **제안 생성 시각 기준**으로 계산하고, 클라이언트 수신 시각으로 계산하지 않는다.

### 3.2 전파

- 클라이언트 연결은 SSE 또는 WebSocket 중 하나를 선택하고 선택 근거를 5단계 문서에 남긴다.
- 파티 확정·제안 생성은 RDB 트랜잭션 커밋 **후에** Redis Pub/Sub으로 발행한다.
- 각 인스턴스는 자신에게 붙은 연결에만 전달한다.
- 발행 실패는 전달 실패로 기록하되, **상태의 권위는 RDB에 있으므로 재조회로 복구 가능해야 한다.**

### 3.3 만료

- 제안 만료 판정은 데이터베이스 시각을 기준으로 한다.
- 만료 처리는 두 경로를 모두 둔다.
  - 예약된 만료 작업
  - 응답 시점의 지연 판정(만료된 제안에 응답이 오면 그 자리에서 거절 처리)
- 두 경로가 동시에 실행돼도 상태 전이가 한 번만 일어나야 한다.

### 3.4 재연결 복구

- 연결이 끊긴 동안 발생한 이벤트는 재전송하지 않는다.
- 재연결 시 **현재 상태 전체를 다시 조회**해서 화면을 맞춘다.
- 이벤트 유실이 화면 불일치로 이어지지 않는지 확인하는 시나리오를 5단계에 포함한다.
  - 연결 끊김 → 그 사이 제안 도착 및 만료 → 재연결 → 화면이 만료 상태를 보여주는가

## 4. 알림

### 4.1 채널

- **브라우저 알림(Web Push)이 기본 채널**이다. 서비스 화면이 열려 있으면 3장의 실시간 전달이 대신한다.
- Discord 다이렉트 메시지는 **사용자가 켠 경우에만** 추가로 보낸다(기능 명세 8.4).
- 알림 채널이 하나도 없는 사용자도 매칭을 신청할 수 있다. 전달 실패는 서비스 이용을 막지 않는다.
- 구독 만료(`410 Gone`)를 감지하면 해당 구독을 지우고 다음 발송 대상에서 제외한다.
- 전송 실패는 재시도하되, 재시도가 INV-5를 깨지 않아야 한다.

### 4.2 지연 큐

- Redis Sorted Set을 쓰고 score를 발송 예정 시각(epoch)으로 둔다.
- 워커는 현재 시각 이하의 항목을 꺼내 발송한다.
- 인스턴스 2대가 같은 항목을 동시에 꺼내는 경우를 6단계의 재현 대상으로 삼는다.

### 4.3 회수

- 파티 취소 시 아직 발송되지 않은 알림을 큐에서 제거한다.
- 제거와 발송이 경합하면 **발송 직전에 파티 상태를 다시 확인**해서 취소된 파티의 알림을 보내지 않는다.
- 큐에서 제거되었으나 이미 워커가 꺼내 든 항목이 있는 경우를 시나리오에 포함한다.

### 4.4 멱등

- 모든 알림에 `dedup_key`를 부여한다. 구성은 `(party_id, user_id, kind, 예정 시각)`이다.
- `dedup_key`에 유니크 제약을 걸고, 발송 기록을 먼저 확정한 뒤 전송한다.
- 전송은 at-least-once로 두고, 중복 차단은 큐가 아니라 **기록 쪽에서** 보장한다.

## 5. 외부 API

### 5.1 신선도 기준 — 요청 생성 시점에만 적용한다

- 티어 정보의 허용 지연을 **10분**으로 둔다.
- 10분 이내의 저장값은 재호출 없이 사용한다.
- 이 값은 캐시 정책의 자유 변수가 아니라 **고정된 제약**이다.
  호출 감소율 목표(6.4)는 이 제약을 지킨 상태에서만 유효하다.
- **신선도는 요청을 만드는 시점에만 강제한다.** 그 시점의 티어를
  `match_request.tier_snapshot`에 고정하고, 이후 매칭은 스냅샷만 읽는다.
- 신선도 위반 계수: **요청 생성 시각과 `tier_snapshot_at`의 차이가 10분을 넘긴 건수**가 0이어야 한다.

> 이 규칙을 "매칭 시점"으로 두면 세 요구가 동시에 성립하지 않는다.
> 배치 처리량 10,000건 / 60초 · 신선도 10분 · Riot 레이트리밋 2분당 100회.
> 레이트리밋상 10분 안에 갱신 가능한 계정은 500개뿐이라 20배가 모자란다.
> 스냅샷을 쓰면 **배치는 Riot을 한 번도 호출하지 않으므로** 모순이 사라진다.

- 부수 효과가 하나 더 있다. 매칭 입력이 불변이 되므로 결정적 FCFS(기능 명세 4.3)가 성립하고,
  배치를 두 번 돌려 같은 결과가 나오는지 검증할 수 있게 된다.
  캐시를 직접 읽으면 두 실행 사이에 티어가 갱신돼 결과가 달라지고,
  중복 배정이 0건이어도 "멱등하다"고 말할 수 없다.
- 확정과 플레이 사이가 먼 예약 파티는 스냅샷이 오래된다.
  준비 확인 시점에 티어를 다시 조회해 게임 규칙상 함께 큐를 잡을 수 있는지 재검증한다
  (기능 명세 7.2). 재검증은 매칭 입력이 아니라 **안내용**이므로 결정성을 깨지 않는다.

### 5.2 호출 병합

- 같은 계정에 대한 동시 조회 요청은 하나로 합친다(single-flight).
- 병합이 인스턴스 내부에서만 일어나는지, 인스턴스 간에도 일어나는지를 구분해 측정한다.
- 인스턴스 2대에서 같은 계정을 동시에 조회하는 시나리오를 7단계에 포함한다.

### 5.3 캐시 스탬피드

- 캐시 항목이 동시에 만료되면 다수 요청이 한꺼번에 외부로 나간다.
- 재현 시나리오는 두 가지다.
  1. 다수 사용자가 같은 계정을 동시에 조회하고 캐시가 그 순간 만료
  2. Redis 재기동으로 캐시 전체 소실
- 대응은 조기 갱신과 만료 시각 지터를 검토하되, **먼저 재현해 호출 폭증을 수치로 남긴다.**

### 5.4 레이트리밋

- Riot 개발용 키의 제한은 1초당 20회, 2분당 100회다. Personal key도 키 단위로 적용된다.
- 애플리케이션 레벨에서 호출량을 제한해 429가 발생하기 전에 막는다.
- 429가 발생한 경우 `Retry-After`를 존중하고, 대기 중 매칭이 멈추지 않도록 저장값으로 진행한다.
- 인스턴스 2대가 같은 키를 공유하므로 **레이트리밋 카운터도 공유 저장소에 둔다.**

## 6. 측정

### 6.1 통과 게이트

- 2장의 INV-1 ~ INV-5.
- 비교 지표가 아니다. 0이면 통과, 1건이라도 있으면 탈락이다.
- 각 단계는 "대응 전 위반 N건 → 대응 후 0건"을 보여야 한다.
  **대응 전 위반이 0건이면 그 단계는 아직 시작하지 않은 것으로 본다.**

### 6.2 비교 지표

| 지표 | 정의 |
|---|---|
| 매칭 요청 생성 p95 | 요청 수신 ~ 응답 반환 |
| 제안 전달 지연 p95 | 파티 확정 트랜잭션 **커밋 시각** ~ 클라이언트 수신 시각 |
| 예약 배치 처리량 | 배치 시작 ~ 종료, 처리 요청 수 |
| 외부 API 호출 수 | 시나리오당 Riot API 실제 호출 횟수 |

- 제안 전달 지연은 인스턴스 시계 차이의 영향을 받으므로 **단일 시계 기준으로 수집**한다.
- 모든 지표는 인스턴스 2대 구성에서 잰다.

### 6.3 부하 프로파일과 입력 분포

**씨드값은 재현성을 보장하지 타당성을 보장하지 않는다.** 입력 분포를 함께 고정한다.

- 티어 분포는 두 조건에서 각각 측정한다.
  1. **균등 분포** — 알고리즘 자체의 성능을 보는 조건
  2. **실제 분포 근사** — 하위·중위 티어에 몰린 실제 롤 분포. 성립률의 현실성을 보는 조건
- 포지션 선호도 균등하지 않게 둔다. 서포터·정글 지원이 적은 실제 경향을 반영한다.
- 두 조건의 결과를 함께 싣고, 어느 쪽 수치인지 명시하지 않은 성립률은 쓰지 않는다.

**매칭 성립률 곡선** — 동시 대기자 10 / 30 / 50 / 100 / 200명 구간에서 성립률과 평균 대기시간을 잰다.
조건을 전부 필수로 처리하는 방식이 실용 수준에 도달하는 지점을 찾고, 조건 완화 도입 근거로 쓴다.

### 6.4 목표 수치와 그 유효 조건

| 항목 | 목표 | 이 목표가 유효한 조건 |
|---|---|---|
| 매칭 요청 생성 p95 | 200ms 이하 | 인스턴스 2대, 동시 대기자 200명 구간 |
| 제안 전달 지연 p95 | 1초 이하 | 참가자가 서로 다른 인스턴스에 분산된 상태 |
| 외부 API 호출 감소율 | 80% 이상 | **신선도 10분(5.1)을 지킨 상태에서.** 이 제약이 없으면 TTL만 늘려도 달성되므로 지표가 아니다 |
| 예약 배치 처리량 | 10,000건 / 60초 | **잠정값.** 아래 참고 |

**예약 배치 처리량이 잠정값인 이유.**
배치가 단순 파이프라인이면 10,000건은 어렵지 않다. 그러나 5인 파티를 주/부 포지션 제약 하에 묶는 것은
조합 탐색이며(문제 7), 롤 하나에 큐 세 종류면 파티션당 수천 건이 한 탐색 공간에 들어간다.
**이 목표치는 8단계에서 배정 알고리즘의 복잡도가 정해진 뒤에 확정한다.**
지금 값은 "이 정도는 나와야 의미가 있다"는 기준선이지 측정 대상이 아니다.

### 6.5 기록 규칙

- 측정 환경(머신 사양, 부하 도구와 옵션, 커넥션 풀 크기), 씨드값, 설정값을 결과와 함께 기록한다.
- 목표 수치를 조정할 경우 **이전 값과 사유를 함께 남긴다.**
- 재현되지 않은 문제는 해결됐다고 말하지 않는다.
