# 실시간 매칭 — 지켜야 할 것

스파이크에서 각자 통째로 짠다. **이 문서에 적힌 것만 맞추고, 나머지는 전부 자율이다.**

## 왜 Redis만 보나

DB 커넥션을 아끼려고 실시간 매칭은 **DB를 참고하지 않는다.** 판정에 필요한 조건이
`req:` JSON 안에 전부 들어 있어서 다른 데를 볼 이유가 없다.

## 이번 단계의 범위

원래 기획은 Core API가 프런트 요청을 받아 Redis에 넣는 구조다. 지금은 실시간 매칭과
Discord만 구현하므로 **Core API 몫을 실시간 매칭 안에 임시로 둔다.**

| 구현한다 | |
|---|---|
| REST 컨트롤러 | 사용자 요청을 받아 Redis에 넣는다 |
| SSE | 제안·확정을 사용자에게 내보낸다 |
| 명단에서 지우기 | 취소 · 만료 · 파티 확정 |

## 1. Redis에 넣는 건 셋뿐

| 키 | 역할 | 내용 |
|---|---|---|
| `mq:...` | 대기 명단 | 누가 먼저 왔는지 순서만 |
| `req:{requestId}` | 주문 메모 | 조건 전부 (아래 JSON) |
| `claim:{requestId}` | "배정 중" 표시 | 파티 짜는 중이니 건들지 마 |

## 2. 주문 메모 JSON

부하 스크립트가 이 모양에 꽂힌다. **필드 이름과 타입을 바꾸지 않는다.**

```json
{
  "requestId": 10482,
  "userId": 7,

  "queue": "SOLO_DUO",
  "targetSize": 5,
  "purpose": "RANK_UP",
  "playMinutes": 120,
  "voiceMode": "POSSIBLE",

  "primaryPosition": "MID",
  "subPositions": ["TOP", "JUNGLE"],

  "tierOrder": 14,
  "allowedTierMinOrder": 11,
  "allowedTierMaxOrder": 18,

  "requestedAt": 1755960000000
}
```

| 필드 | 뜻 |
|---|---|
| `queue` | 어떤 큐 |
| `targetSize` | 몇 명 파티 |
| `purpose` | 플레이 목적 |
| `playMinutes` | 몇 시간 할 건지 |
| `voiceMode` | 음성 채팅 |
| `primaryPosition` | 주 포지션 |
| `subPositions` | 부 포지션 |
| `tierOrder` | 내 티어 (숫자) |
| `allowedTierMinOrder` · `allowedTierMaxOrder` | 같이 할 티어 하한 · 상한 |
| `requestedAt` | 신청 시각. 순서용 |

## 3. 매칭 루프가 하는 일

1. 대기 명단을 읽는다
2. 메모를 보고 같이 앉힐 인원을 찾는다
3. 찾은 전원에게 **동시에** `claim`을 건다. 하나라도 이미 걸려 있으면 전부 취소하고 다음 사이클
4. 확정을 `PUBLISH`로 알린다

지워진 요청은 **명단에 없으니 그냥 넘어간다.** 매칭이 따로 확인하지 않는다.

## 4. 구현할 기능

카톡에 올린 기능명세서의 **실시간 매칭 서비스** 항목을 따른다.

# 자율 — 아래는 각자 정한다

위 넷 말고는 **앞에서 합의하지 않는다.** 판정일에 코드를 놓고 고른다.

- `claim`을 어떤 키·자료구조로 표현할지, TTL을 얼마로 둘지, 언제 뗄지
- 명단을 한 번에 몇 개 읽을지 — 파이프라인 · 커서 · 통째로
- 루프를 언제 돌릴지 — 폴링 주기, 요청마다 깨우기, 인스턴스 몇 대가 돌릴지
- Lua를 몇 개로 쪼갤지, 무엇을 Lua 안에서 풀지
- 취소 · 만료 · 확정이 명단에서 이름을 지우는 방식
- 만료를 무엇으로 판정할지 — TTL · 별도 필드 · 서버 시각
- 패키지 구조, 클래스 분리, 테스트 방식

**골격을 미리 나눠주지 않는다.** 골격을 주면 구조가 딸려가서 비교할 것이 코드 스타일만 남는다.
