# PRD — party-matcher

> 리그 오브 레전드 파티 자동 매칭 서비스. Port-051 · SW마에스트로 17기 · 6개월

이 문서는 **무엇을 왜 만드는가**를 고정한다.
구현 방법은 `01-functional-spec-mvp.md`, 불변식과 측정 기준은 `02-technical-spec-supplement.md`에 있다.

이 문서의 모든 수치는 측정 방법을 함께 적었다. 근거 없는 숫자는 쓰지 않는다.

## 1. 한 줄

트롤에 데인 직후, 발품 없이, 조건이 맞는 팀원을 서버가 묶어준다.

## 2. 배경 — 사용자는 언제 이걸 여는가

평소엔 파티를 찾지 않는다. 니즈는 **특정 순간에만 격발된다.**

솔로랭크를 돌렸다. 팀원이 트롤이었다. 한 판을 통째로 날렸고, 지금 게임을 끌지 한 판 더 할지
고민 중이다. 이때 "정상적인 사람들과 하고 싶다"는 생각이 처음 든다.

그래서 게시판을 뒤진다. 그런데 올라오는 글의 상당수가 클랜·디스코드 서버 모집이다.
들어가려면 서버에 가입하고, 규칙을 읽고, 자기소개를 하고, 사람 많은 채널에서 눈치를 보며
"같이 하실 분?"을 외쳐야 한다.

한 판 하려고 이걸 다 하지는 않는다. 그냥 참고 혼자 돌린다.

### 2.1 기존 경로가 왜 안 되는가

| 경로 | 안 되는 이유 |
|---|---|
| 게시판 (인벤 · op.gg 듀오) | 비동기다. 글을 쓰고 기다리는 동안 빡침이 식거나 게임을 끈다 |
| 디스코드 커뮤니티 서버 | 가입·자기소개가 선행된다. 한 판의 대가로 지불하기엔 크다 |
| 기존 LFG 봇 (LFG Hub · Teamplay) | 디스코드 봇이라 서버 안에서만 동작한다. 최소 한 곳엔 가입해야 한다 |

아무도 **"발품 없이, 지금, 한 판"**을 주지 않는다. 이 서비스가 서는 자리가 거기다.

### 2.2 측정한 것

인벤 LoL 파티 매칭 게시판 1페이지 73건 분류 (2026-08-18)

- 클랜·디스코드 서버 모집 **60.3%**
- 일회성 매칭 **6.8%**
- 같은 제목 도배 **42.5%**

→ 게시판 이름은 "파티 매칭"이지만 실제로는 **클랜 모집 게시판**이다.

**이 숫자의 한계.** 6.8%는 *포기하지 않고 글까지 쓴 사람*의 비율이다.
포기한 사람은 어디에도 흔적을 남기지 않으므로 **이 숫자를 수요의 크기로 읽으면 안 된다.**
읽을 수 있는 것은 "게시판이 일회성 매칭 용도로 작동하지 않는다"는 사실 하나뿐이다.

## 3. 목표 / 비목표

**목표**

- 요청을 넣은 사람이 발품 없이 조건이 맞는 팀원을 배정받는다
- 배정은 **서버가 확정한다.** 사람이 서로를 찾아다니지 않는다
- 한 번 괜찮았던 사람과 **다시 만날 수 있다**

**비목표**

- 커뮤니티를 만드는 것 — 클랜·길드·친목은 이미 디스코드가 한다
- 실력을 올려주는 것 — 코칭·강의·대리는 다루지 않는다
- 게임 내 매칭을 대체하는 것 — 우리는 **게임에 들어가기 전** 파티를 만든다

## 4. 타깃 사용자

**주 사용자** — 솔로랭크를 주로 돌리고, 함께 할 고정 팀원이 없으며,
커뮤니티 가입에 거부감이 있는 한국 서버 이용자.

**MVP 제외** — 이미 5인 팀이 있는 사람, 대리·부스팅 목적, 미성년자(운영 부담).

## 5. 범위

### 5.1 왜 롤 하나인가

매칭은 밀도가 전부다. 게임을 늘리면 대기자가 갈라져 성립률이 떨어진다.
게임별 연동·오류 분기·조건 스키마에 드는 시간은 동시성 과제에서 그대로 빠져나간다.

게임 추가는 코드가 아니라 **설정으로 처리할 수 있게 설계**하되, MVP에는 롤 하나만 등록한다.

### 5.2 왜 듀오가 1순위인가

게임 규칙이 정한다. 리그 오브 레전드의 큐별 동반 인원 제한은 다음과 같다.

| 큐 | 함께 큐 가능한 인원 |
|---|---|
| 솔로 · 듀오 랭크 | 1인 또는 2인만 |
| 자유 랭크 | 1, 2, 3, 5인 (4인 불가) |
| 일반전 | 1–5인 |

배경 시나리오가 "솔로랭크를 돌렸다"이므로, 그 사용자가 취할 수 있는 행동은 **듀오뿐**이다.

정원이 작을수록 성립률도 유리하다. 정원 2는 후보 **1명**만 찾으면 되고,
정원 5는 **4명을 동시에** 찾아야 하며 포지션까지 겹치지 않아야 한다.

> 큐별 인원 제한은 Riot의 정책 변경 대상이다. 구현 전 현재 규칙을 재확인할 것.
> 허용 티어 범위도 마찬가지이므로 설정 데이터로 관리한다(`01` 3.5).

### 5.3 제품 시나리오와 검증 시나리오는 다르다

이 프로젝트는 서비스인 동시에 **동시성 설계의 검증 대상**이다. 두 목적이 요구하는 시나리오가 다르다.

| | 시나리오 | 이유 |
|---|---|---|
| **제품 P0** | 솔로·듀오 랭크 (정원 2) | 격발 시점의 사용자가 실제로 취할 수 있는 행동 |
| **검증 P0** | 자유 랭크 (정원 5) | 포지션 배정과 **좌석 경합**이 여기서만 발생한다 |

**둘 다 P0로 남긴다.** 정원 2에서는 한 명이 나가면 남은 인원이 1명이라 파티가 그냥 취소되고,
빈자리를 놓고 경쟁할 좌석이 생기지 않는다. 정원 5가 빠지면
**INV-1(정원 초과)을 재현할 경로 자체가 사라진다**(`02` 2장).

일반전은 P1이다.

## 6. 핵심 사용자 흐름

```
[격발] 솔랭 한 판 망함
   ↓  10초 이내
1. 진입     Riot ID 입력 → 티어·포지션 자동 조회
2. 조건     큐 · 티어 범위 · 포지션 (필수 3)
3. 대기     현재 큐 인원과 남은 시간 표시
   ↓
4. 제안     조건이 맞는 상대와 묶임. 전원에게 동시 발송
5. 수락     제한시간 내 전원 수락 시 확정
6. 합류     Riot ID 공개 → 게임 클라이언트에서 초대
   ↓  게임 종료 후
7. 평가     "또 하고 싶다 / 아니다" 1클릭
```

### 6.1 설계 제약 — 10초

**1번에서 3번까지 10초 안에 끝나야 한다.** 빡친 사람은 폼을 채우지 않는다.

이 제약이 다음을 결정한다.

- 필수 입력은 **큐·티어 범위·포지션 3개**뿐이다. 나머지는 전부 기본값을 채워 두고 접어 둔다
- 프로필(닉네임·음성·목적·분위기)은 최초 1회만 받고 이후 요청에 재사용한다
- Riot ID는 등록해 두고 재입력받지 않는다
- 조건 입력 화면에서 **현재 대기 인원**을 보여준다. 성립 가능성을 즉시 알 수 있어야 조건을 조정한다
