## 2. 언어와 프레임워크

### 2.1 Java 21

LTS이고, **가상 스레드가 이 프로젝트의 부하 모양과 맞는다.**

기술 명세 3장의 제안 팬아웃은 사용자마다 SSE 연결을 하나씩 붙들고 있는 구조다.
플랫폼 스레드로 이걸 받으면 대기 중인 연결 하나가 스레드 하나를 잡아먹는다.
6.3의 측정 구간이 동시 대기자 200명까지 올라가고, 부하 발생기 쪽도 같은 수의 연결을 열어야 하므로
연결당 스레드 모델은 측정 자체를 방해한다.

Java 25·26도 선택할 수 있지만 **올릴 이유가 없다.** 필요한 기능은 21에 다 있다.

### 2.2 Spring Boot 4.1.0

Spring Initializr의 현행 기본값이다. 3.5 계열은 이미 신규 생성 선택지에서 내려갔으므로
새로 시작하는 프로젝트가 3.x를 고를 이유는 없다.

**다만 생태계 시차를 감수한다.** Boot 4는 Spring Framework 7 기반이라 서드파티 라이브러리가
아직 따라오지 못한 경우가 있다. Spring Cloud AWS는 4.0.0이 Boot 4.x를 지원하는 것을 확인했고,
그 외 의존성은 **추가하는 시점에 Boot 4 지원 여부를 먼저 확인한다.**
지원이 없으면 라이브러리를 바꾸지 스프링 버전을 내리지 않는다.

### 2.3 Gradle + Kotlin DSL

`.gitignore`가 이미 Gradle을 전제하고 있었다(`.gradle/`, `gradle-wrapper.jar`).

**멀티모듈로 간다.** ERD 문서가 반영한 아키텍처에서 실행기는 다섯이다 —
Core API, 즉시 매칭 서비스, 예약 매칭 Worker, Notification Worker, Discord Worker.
이들은 도메인과 스키마를 공유하지만 배포·기동 단위가 다르므로 모듈로 갈린다.

**단, 처음부터 다섯으로 쪼개지 않는다.** 0단계에 필요한 모듈만 만들고
실행기는 해당 단계에서 분리한다(8장). 버전은 Gradle version catalog(`libs.versions.toml`)로 한곳에 모은다.

### 2.4 왜 WebFlux가 아닌가

**README가 정의한 문제 일곱 중 논블로킹 I/O를 요구하는 것이 없다.**

| 흔한 도입 이유 | 이 프로젝트에서는 |
|---|---|
| SSE 같은 스트리밍이 필요하다 | MVC의 `SseEmitter`로 된다 |
| 연결당 스레드가 부담이다 | 가상 스레드가 같은 문제를 푼다(2.1) |
| 외부 API 호출이 많다 | Riot 호출은 캐싱·병합으로 줄이는 게 7단계 과제다. 동시성 모델 문제가 아니다 |

반대로 WebFlux를 고르면 **잃는 것이 분명하다.** R2DBC로 넘어가면 2단계의 비관적 락·낙관적 락 비교가
`@Lock(PESSIMISTIC_WRITE)`·`@Version`이라는 표현 수단을 잃고, JPA를 유지한 채 WebFlux를 쓰면
블로킹 호출을 별도 스케줄러로 밀어내는 코드가 전 구간에 붙는다.

이 저장소가 설명해야 하는 것은 **제약을 어디에 두었는가**이지 어떤 동시성 모델을 썼는가가 아니다.

## 3. 데이터

### 3.1 PostgreSQL + Spring Data JPA

권위 있는 상태는 전부 RDB에 있다(기술 명세 1.3). 그리고 **불변식을 강제하는 제약이 여기 박힌다** —
`party_member.request_id` UNIQUE가 INV-3을, `notification_job.dedup_key` UNIQUE가 INV-5를 막는 식이다.

JPA를 고르는 실질적인 이유는 2단계다. 락 전략 셋을 비교하는데, 앞의 둘이 JPA에서 선언 하나로 갈린다.

| 전략 | JPA 표현 |
|---|---|
| 비관적 락 | `@Lock(LockModeType.PESSIMISTIC_WRITE)` |
| 낙관적 락 | `@Version` |
| 파티션 단일 라이터 | 락을 쓰지 않는다. 애플리케이션 구조로 푼다 |

비교군이 같은 영속성 계층 위에 서야 처리량 차이를 락 전략 탓으로 돌릴 수 있다.

### 3.2 위반 검출은 JPA를 우회한다

기술 명세가 **"위반 검출은 로그가 아니라 데이터베이스를 직접 검사해서 계수한다"**고 못박았다.

그래서 검출기는 JPA를 타지 않고 **JdbcTemplate + 네이티브 SQL**로 쓴다.
영속성 컨텍스트 1차 캐시나 지연 로딩이 끼면 "지금 DB에 무엇이 들어 있는가"가 아니라
"이 세션이 무엇을 봤는가"를 세게 된다. 통과 게이트를 재는 도구가 그러면 안 된다.

### 3.3 Flyway

**제약이 곧 불변식이므로, 제약은 리뷰 대상이어야 한다.**

JPA의 `ddl-auto`로 스키마를 만들면 유니크 제약이 어노테이션 속성에 흩어지고
어느 PR에서 무엇이 바뀌었는지 diff로 안 보인다. 마이그레이션을 SQL 파일로 두면
`ALTER TABLE ... ADD CONSTRAINT`가 리뷰어 눈앞에 온다.
ERD 4장이 불변식과 제약을 1:1로 대응시켜 둔 문서라 그 대응이 코드에서도 유지돼야 한다.

`ddl-auto`는 `validate`로 둔다. 스키마를 만들지는 않고 엔티티와 어긋나면 기동에 실패하게 한다.

### 3.4 Redis

기술 명세 1.3이 위치를 이미 지정했다 — 분산 락, Pub/Sub, 지연 큐, 캐시.
클라이언트는 Spring Boot 기본값인 **Lettuce**를 쓴다.

**Redisson은 지금 넣지 않는다.** 4단계 과제가 "락 만료 중 작업 지속"인데,
이건 만료만 있고 연장이 없는 소박한 락을 먼저 만들어 **깨지는 것을 확인한 뒤**
watchdog이 있는 구현과 비교하는 순서다. 처음부터 Redisson을 깔면 재현할 문제가 사라진다.
따라서 Redisson은 4단계의 **비교군으로** 들어온다.

### 3.5 SQS

ERD 5장이 큐 두 개(`notification-events`, `discord-commands`)를 전제하고,
둘 다 at-least-once에 재시도·DLQ가 붙어 있다.
**Spring Cloud AWS 4.0.0**을 쓴다(3.4.x가 Boot 3.5 계열 마지막이라 4.0.0이어야 한다).

로컬에서는 **LocalStack**으로 큐를 띄운다. 실제 AWS 계정에 붙는 것은 배포 단계의 문제다.

## 4. 부하 발생기 — 둘을 쓴다

부하 발생기는 하나로 정할 수 있는 항목이 아니었다. **재야 하는 것이 다섯이고 모양이 다르다.**

| 측정 대상 | 모양 | 도구 |
|---|---|---|
| 매칭 요청 생성 p95 ≤ 200ms | stateless POST | **k6** |
| 외부 API 호출 감소율 · 캐시 스탬피드(7단계) | 캐시를 비우고 동시에 몰아치기 | **k6** |
| 예약 배치 처리량 10,000건 / 60초 | 데이터 적재 + 배치 기동 | 자체 모듈 |
| 제안 전달 지연 p95 ≤ 1초 | SSE 연결을 유지한 채 응답 | **자체 모듈** |
| 매칭 성립률 곡선 (10/30/50/100/200) | 요청 → SSE 대기 → 수락 전 구간 | **자체 모듈** |

### 4.1 경계는 SSE다

가상 사용자 한 명이 이렇게 움직여야 하는 시나리오가 있다.

```
매칭 요청 생성(POST) → SSE 스트림 열고 대기 → 제안 수신 → 수락/거절(POST)
                                              ↑ 일부는 응답하지 않고 만료시킨다
```

즉 **SSE 연결을 붙든 채로 HTTP 요청을 보내야 한다.** k6는 SSE가 코어 기능이 아니라
커뮤니티 확장(`k6/x/sse`)이고, 연결이 열려 있는 동안 이벤트 루프를 블록한다.
우회하려면 SSE를 붙드는 VU 풀과 요청을 보내는 VU 풀을 나눠야 하는데,
k6의 VU는 서로 격리돼 있어 "이 사용자가 받은 제안을 이 사용자가 수락한다"는 상관관계를 잇기 어렵다.

**상태가 걸리면 자체 모듈, 걸리지 않으면 k6.** 이 한 줄이 배치 기준이다.

### 4.2 자체 모듈이 추가로 얻는 것

- **씨드 기반 입력 분포** — 6.2가 균등 분포와 실제 티어 분포 두 조건을 요구한다. `Random(seed)`로 재현한다.
- **위반 검출과 한 프로세스** — 부하를 넣은 그 도구가 같은 JDBC 연결로 3.2의 검출 쿼리를 돌리고 한 리포트로 낸다.
- **API 계약 변경이 컴파일 에러로 잡힌다** — 백엔드 DTO·enum을 그대로 참조한다.
  `CONTRIBUTING.md`가 "API 계약은 6개월 내내 흔들린다"고 적어 둔 상태에서 이 결합은 비용이 아니라 이득이다.

### 4.3 자체 모듈에 붙는 조건

직접 만드는 이상 **측정이 정직하다는 것을 스스로 보여야 한다.** 다음 둘은 선택이 아니다.

- **open model로 짠다.** 동시 사용자 수를 고정하는 게 아니라 **초당 요청 도착률**을 고정한다.
  서버가 느려져도 요청은 계속 도착해야 대기 큐가 자라고, 그래야 p95가 부하를 반영한다.
- **지연은 보내려고 의도한 시각부터 잰다.** 실제로 보낸 시각부터 재면
  서버가 느릴수록 요청을 덜 보내게 되어 p95가 실제보다 좋게 나온다(coordinated omission).

k6가 executor를 `constant-arrival-rate`와 `ramping-vus`로 나눠 둔 것이 같은 구분이다.
두 도구를 같은 모델로 맞춰야 4장의 표를 가로질러 수치를 비교할 수 있다.

### 4.4 k6는 0단계에 넣지 않는다

k6가 필요한 두 측정은 1단계와 7단계에 있다. 러닝 커브가 낮은 도구라 미리 깔아 둘 이득이 없고,
해당 단계에서 스크립트를 추가하면 된다. 0단계에 필요한 것은 성립률 곡선과 위반 검출이고 둘 다 자체 모듈 쪽이다.

## 5. 관측

**Prometheus·Grafana가 필요한 이유는 대시보드를 그리기 위해서가 아니다.** 부하 도구가 그리는 그림은
밖에서 본 것(요청 수, 응답 시간, 에러율)이고, 그건 각 도구가 자체적으로 낸다.
정작 필요한 것은 서버가 **그 시간을 어디서 썼는가**다.

2단계가 이걸 요구한다. 락 전략 셋을 비교할 때 "A가 B보다 처리량이 높다"는 부하 도구가 알려주지만,
"A는 락 대기에서, B는 낙관적 락 재시도에서 시간을 쓴다"는 서버 안을 봐야 나온다. 비교의 결론이 후자여야 한다.

그래서 **계측과 시각화를 분리해 도입한다.**

| | 무엇 | 언제 |
|---|---|---|
| 계측 | Spring Boot Actuator + Micrometer | **0단계.** 의존성 두 줄이고 `/actuator/prometheus`가 텍스트로 열린다 |
| 시각화 | Prometheus + Grafana를 Compose에 추가 | **2단계.** 계측이 돼 있으므로 스크랩 설정만 붙인다 |

0단계의 통과 게이트(정원 초과·중복 배정·알림 중복)는 애초에 DB 직접 검사로 계수하므로
메트릭 파이프라인이 없어도 잰다.

## 6. 로컬 실행 환경

**Docker Compose.** 기술 명세 1.2가 "모든 측정은 인스턴스 2대 이상에서 수행한다"고 못박았고,
1.1 구성도에 LB가 그려져 있다. 이 구성이 로컬에서 그대로 서지 않으면 재현이 불가능하다.

```
nginx (LB) ──┬── app #1 ──┬── PostgreSQL
             └── app #2 ──┼── Redis
                          └── LocalStack (SQS)
```

**테스트는 Testcontainers.** 3.1의 제약이 실제로 위반을 막는지 확인하려면 진짜 PostgreSQL이 필요하다.
H2로는 검증하려는 대상 자체가 없어진다.

## 7. 저장소 배치

`CONTRIBUTING.md` 1절의 구조를 유지하되 `backend/` 안을 Gradle 서브프로젝트로 나눈다.

```
backend/
├── settings.gradle.kts
├── gradle/libs.versions.toml   버전 카탈로그
├── common/                     도메인 모델 · 엔티티 · Flyway 마이그레이션
├── core-api/                   Core API. 인스턴스 2대로 띄우는 대상
├── load-generator/             자체 부하 발생기 + 위반 검출기 (4장)
└── load-test/                  k6 스크립트 (4.4에 따라 나중에 추가)
```

- 부하 발생기를 **별도 서브프로젝트**로 두는 이유는 측정 도구가 측정 대상의 의존성 그래프에 섞이면 안 되기 때문이다.
- 실행기 넷(즉시 매칭 서비스, 예약 매칭 Worker, Notification Worker, Discord Worker)은
  해당 단계에서 모듈로 추가한다. 지금 빈 모듈을 만들어 두지 않는다.

## 9. 아직 정하지 않은 것

### 9.1 프론트엔드

**미정이다.** 0단계 과제(도메인 모델·상태 기계·부하 발생기·위반 검출기)에 프론트엔드가 필요하지 않고,
API 계약이 아직 흔들린다.

**정하는 시점** — Core API가 제안 전달까지 동작해서 붙일 화면이 의미를 갖는 때. 로드맵상 5단계 전후다.
그때 판단할 것은 SSE 수신과 Web Push(VAPID)를 어디서 처리하는가이며,
`site/`가 이미 Vercel에 배포 중이므로 배포 경로 분리도 같이 정한다.

### 9.2 알림 지연 처리

기술 명세 1.3은 Redis Sorted Set을, ERD 5장은 SQS를 적고 있다.
ERD가 이미 짚었듯 SQS의 `DelaySeconds`는 최대 15분이라 "시작 10분 전" 같은 장기 예약을 큐만으로 못 건다.
`fire_at` 폴링과 EventBridge Scheduler 중 무엇을 쓸지는 **6단계에서 정한다.**

### 9.3 좌석 선점 구현

ERD가 짚었듯 아키텍처 도면의 Lua 선점은 README 2단계의 **비교 대상**이지 확정이 아니다.
측정 전에는 확정으로 읽지 않는다.

## 10. 무엇이 바뀌면 재검토하는가

| 결정 | 재검토 조건 |
|---|---|
| Java 21 | 21에 없는 기능이 실제로 필요해질 때. "새 LTS가 나와서"는 사유가 아니다 |
| Spring Boot 4.1 | 필요한 라이브러리가 Boot 4를 지원하지 않고 대체재도 없을 때 |
| Spring MVC | 가상 스레드로 감당이 안 되는 부하가 **측정으로** 확인될 때. 예상으로 바꾸지 않는다 |
| JPA | 락 전략 비교(2단계)가 끝난 뒤 JPA가 병목으로 측정될 때 |
| 자체 부하 발생기 | k6가 SSE 병렬 연결을 코어에서 지원하게 될 때. 그러면 4장의 경계가 사라진다 |
| Prometheus·Grafana 2단계 도입 | 그 전 단계에서 서버 내부 지표가 필요해질 때 앞당긴다 |
| 멀티모듈 | 실행기 분리가 과하다고 판명되면 프로필 기반 단일 모듈로 되돌린다 |

> 이 표에 없는 이유로 스택을 바꾸려면 그 이유를 여기 먼저 추가한다.
