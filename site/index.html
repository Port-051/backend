Doc 00 · PRD

왜 만드는가

트롤에 데인 직후, 발품 없이, 조건이 맞는 팀원을 서버가 묶어준다.

이 문서의 모든 수치는 측정 방법을 함께 적었다. 근거 없는 숫자는 쓰지 않는다.

사용자는 언제 이걸 여는가

평소엔 파티를 찾지 않는다. 니즈는 특정 순간에만 격발된다.

솔로랭크를 돌렸다. 팀원이 트롤이었다. 한 판을 통째로 날렸고, 지금 게임을 끌지 한 판 더 할지 고민 중이다. 이때 "정상적인 사람들과 하고 싶다"는 생각이 처음 든다.

그래서 게시판을 뒤진다. 그런데 올라오는 글의 상당수가 클랜·디스코드 서버 모집이다. 들어가려면 서버에 가입하고, 규칙을 읽고, 자기소개를 하고, 사람 많은 채널에서 눈치를 보며 "같이 하실 분?"을 외쳐야 한다.

한 판 하려고 이걸 다 하지는 않는다. 그냥 참고 혼자 돌린다.

기존 경로가 왜 안 되는가

경로안 되는 이유
게시판 (인벤 · op.gg 듀오)비동기다. 글을 쓰고 기다리는 동안 빡침이 식거나 게임을 끈다
디스코드 커뮤니티 서버가입·자기소개가 선행된다. 한 판의 대가로 지불하기엔 크다
기존 LFG 봇 (LFG Hub · Teamplay)디스코드 봇이라 서버 안에서만 동작한다. 최소 한 곳엔 가입해야 한다

아무도 "발품 없이, 지금, 한 판"을 주지 않는다. 이 서비스가 서는 자리가 거기다.

측정한 것

인벤 LoL 파티 매칭 게시판 1페이지 73건 분류 (2026-08-18)

클랜 · 서버 모집60.3%
일회성 매칭6.8%
같은 제목 도배42.5%

게시판 이름은 "파티 매칭"이지만 실제로는 클랜 모집 게시판이다.

이 숫자의 한계

6.8%는 포기하지 않고 글까지 쓴 사람의 비율이다. 포기한 사람은 어디에도 흔적을 남기지 않으므로 이 숫자를 수요의 크기로 읽으면 안 된다. 읽을 수 있는 것은 "게시판이 일회성 매칭 용도로 작동하지 않는다"는 사실 하나뿐이다.

목표와 비목표

목표
  • 요청을 넣은 사람이 발품 없이 조건이 맞는 팀원을 배정받는다
  • 배정은 서버가 확정한다. 사람이 서로를 찾아다니지 않는다
  • 한 번 괜찮았던 사람과 다시 만날 수 있다
비목표
  • 커뮤니티를 만드는 것 — 클랜·길드·친목은 이미 디스코드가 한다
  • 실력을 올려주는 것 — 코칭·강의·대리는 다루지 않는다
  • 게임 내 매칭을 대체하는 것 — 우리는 게임에 들어가기 전 파티를 만든다

타깃 사용자

주 사용자 — 솔로랭크를 주로 돌리고, 함께 할 고정 팀원이 없으며, 커뮤니티 가입에 거부감이 있는 한국 서버 이용자.

MVP 제외 — 이미 5인 팀이 있는 사람, 대리·부스팅 목적, 미성년자(운영 부담).

왜 듀오가 1순위인가

게임 규칙이 정한다. 리그 오브 레전드의 큐별 동반 인원 제한은 다음과 같다.

큐함께 큐 가능한 인원비고
솔로 · 듀오 랭크1인 또는 2인격발 시점의 사용자가 취할 수 있는 유일한 행동
자유 랭크1, 2, 3, 5인4인 불가 — 게임 규칙
일반전1–5인—

배경 시나리오가 "솔로랭크를 돌렸다"이므로, 그 사용자가 취할 수 있는 행동은 듀오뿐이다. 정원이 작을수록 성립률도 유리하다 — 정원 2는 후보 1명만 찾으면 되고, 정원 5는 4명을 동시에 찾아야 하며 포지션까지 겹치지 않아야 한다.

제품 시나리오와 검증 시나리오는 다르다

이 프로젝트는 서비스인 동시에 동시성 설계의 검증 대상이다. 두 목적이 요구하는 시나리오가 다르다.

구분시나리오이유
제품 P0솔로 · 듀오 (정원 2)격발 시점의 사용자가 실제로 취할 수 있는 행동
검증 P0자유 랭크 (정원 5)포지션 배정과 좌석 경합이 여기서만 발생한다
P1일반전—
둘 다 P0로 남긴다

정원 2에서는 한 명이 나가면 남은 인원이 1명이라 파티가 그냥 취소되고, 빈자리를 놓고 경쟁할 좌석이 생기지 않는다. 정원 5가 빠지면 INV-1(정원 초과)을 재현할 경로 자체가 사라진다.

Doc 01 · Overview

개요

문제·해결·MVP 범위. 이 문서가 무엇을 고정하려는지.

이 문서 묶음의 목적: 무엇을 만드는지가 아니라 무엇이 깨지면 실패로 보는지를 먼저 고정하는 것. 기능 목록은 우선순위와 함께, 동시성 문제는 검출 질의와 함께 적는다. 재현되지 않은 문제는 해결됐다고 말하지 않는다.

문제

같이 게임할 사람을 구하는 경로가 전부 사람 응답 대기로 막혀 있다. 디스코드 구인 글 → 누군가 읽기를 기다림 → DM → 조건 확인 → 합류. 각 단계가 멈춰 있어 실제로는 아는 사람에게 연락하거나 혼자 랜덤 매칭을 돌린다.

조건이 취향 문제가 아니라는 점이 이 문제의 성격을 정한다. 티어 범위·포지션·음성채팅·플레이 목적이 어긋나면 파티는 성립해도 그 판은 서로에게 손해다. 매칭이 느린 게 문제가 아니라, 조건을 맞추는 비용이 커서 아무도 안 하는 것이다.

해결

조율 단계를 없앤다. 한 사람의 요청을 조건이 맞는 후보 전원과 맞춰보고, 정원만큼 묶어 서버가 확정한다. 그래서 이건 게시판 문제가 아니라 배정(assignment) 문제다.

MVP 범위

롤 하나만

매칭은 밀도가 전부라 게임을 늘리면 대기자가 갈라져 성립률이 떨어진다. 게임별 연동·오류 분기·조건 스키마에 드는 시간은 동시성 과제에서 그대로 빠져나간다. 게임 추가는 코드가 아니라 설정으로 처리할 수 있게 설계하되, MVP에는 롤 하나만 등록한다.

  • 신원은 Discord 계정으로 확인한다. 익명 식별자를 쓰지 않으므로 기기를 바꿔도 상태가 이어진다.
  • 티어는 Riot API 실측값이다. 자기 신고가 아니다. 다만 입력한 Riot ID가 본인 계정인지는 검증하지 못하며, 이 한계를 화면에 표시한다.
  • 알림은 서비스 화면과 브라우저 알림으로 보낸다. 외부 메신저 설정을 요구하지 않는다. Discord 다이렉트 메시지는 원하는 사람만 켜는 선택 옵션이다.
  • 확정된 파티에는 Discord 전용방을 자동으로 만든다. 확정 이후의 연락 수단이며, 서버 가입은 확정의 전제 조건이 아니다. 전용방이 없어도 파티는 성립한다.

제외 — PUBG · Steam 게임, Riot Sign On, 일치도 점수, 조건 자동 완화, 반복 예약, 신고 · 내부 신뢰도 점수, 운영자 화면.

평가 · 차단 · 재회는 포함한다. 조건만으로 만난 사람과 다시 만날 수 없으면 이 서비스는 일회용이 된다. 재회는 조건을 완화하지 않고 통과한 후보 안에서 순서만 앞당긴다.

문제 정의

게시판을 빠르게 만드는 것으로는 풀리지 않는 일곱 가지.

#문제성격검증

1·2번이 핵심이다

2번은 이 서비스에 원래 있는 문제다. 요청 하나가 동시에 두 후보 파티에 묶이면 사용자는 같은 시간에 두 파티에 들어간다. 단일 행 카운터가 아니라 요청·시간·포지션이 얽힌 교차 제약이라, 재고 차감보다 제약을 표현하는 것 자체가 어렵다.

1번은 빈자리 충원 때문에 생긴다. 서버가 정원만큼 묶어 제안하고 전원 수락해야 확정하는 구조에서는 자리를 놓고 경쟁하는 사람이 없다. 정원 초과는 확정된 파티에서 이탈자가 나와 그 자리를 공개 모집할 때 비로소 발생한다. 5인 파티에서 한 명 빠졌다고 파티 전체를 버리는 건 낭비이므로 충원은 실제로 필요한 기능이고, 그 기능이 좌석 경합을 만든다. 빈자리는 포지션 단위로 열리므로 경합 대상은 파티 정원이 아니라 특정 포지션의 좌석 하나다.

3번은 성격이 다르다. 예약 매칭은 수락 없이 자동 확정되므로, 배치가 두 번 돌면 사용자는 자기가 모르는 파티에 두 번 들어간다. 사후 취소로 수습할 수 없다.

Doc 03 · Architecture

아키텍처

그림은 한 장이다. 역할 계층과 배포 경계를 따로 그리면 둘이 어긋나고, 어긋났을 때 어느 쪽이 맞는지 판정할 근거가 없다. 인스턴스 2대를 전제한다.

실선 — 요청 · 쓰기 점선 — 이벤트 · 전파 · 관측
1

좌석 경합 (INV-1) — 두 인스턴스가 같은 포지션 좌석을 동시에 확정하면 정원을 넘긴다. 빈자리 공개 모집(F4·F5)이 이 경합을 만드는 유일한 경로다.

2

중복 배정 (INV-2) — 서로 다른 인스턴스가 같은 사용자를 시간이 겹치는 두 파티에 넣는다. 단일 행 카운터가 아니라 사용자·시간 구간의 교차 제약이라 표현부터 어렵다.

3

배치 중복 실행 (INV-3) — 두 스케줄러가 00시 배치에 동시 진입하거나, 락 TTL이 만료된 뒤에도 첫 실행이 쓰기를 계속한다. 멱등성은 락이 아니라 조건부 쓰기로 보장한다.

흐름은 왼쪽에서 오른쪽으로 읽는다 — 웹과 로드밸런서에서 들어와 다섯 실행기를 지나 저장소에서 끝난다. 회색 면 안의 다섯 상자는 한 인스턴스의 실행기이고, ×2는 그 실행기가 인스턴스 2대에서 각각 돈다는 뜻이다. 역할이 나뉘어 있지 않기 때문에 세 경합이 모두 성립한다. 점선 테두리 상자는 측정 도구로, 운영 구성이 아니다. 간선은 흐름과 경합을 정하는 것만 남겼다.

왜 2대인가

인스턴스가 하나면 애플리케이션 내부 락만으로 좌석 경합과 중복 배정이 막힌다. 막히면 문제가 재현되지 않고, 재현되지 않으면 데이터베이스 제약과 분산 락의 필요성을 증명할 수 없다. 문제 3·4·5번은 아예 인스턴스가 둘 이상일 때만 나타난다.

불변식

통과 게이트다. 비교 지표가 아니다. 각 검사 질의가 0행을 반환해야 통과하고, 1행이라도 나오면 탈락이다.

검출은 로그가 아니라 데이터베이스를 직접 검사한다 — 위반이 발생했는데 로그에 안 남는 경우가 가장 위험하기 때문이다.

INV-1 정원 초과 문제 1 · M1

확정된 파티의 인원은 목표 인원을 넘지 않는다. 이 위반은 F4·F5 빈자리 모집 경로에서만 발생하고, 그 경로가 실제로 열리는 것은 예약 파티뿐이다 — 즉시 매칭 파티는 확정 시각이 곧 시작 시각이라 모집 창이 따로 정의돼야 한다. 다섯 불변식 중 유일하게 단순 제약으로 막을 수 없다. 정원은 행 하나의 속성이 아니라 집합의 크기이기 때문이며, 그래서 M1·M2가 이 프로젝트의 본체다.

검사 질의 
SELECT p.id, p.target_size, COUNT(pm.request_id) AS actual
FROM party p
JOIN party_member pm ON pm.party_id = p.id
WHERE p.status IN ('CONFIRMED', 'RECRUITING')
  AND pm.left_at IS NULL
GROUP BY p.id, p.target_size
HAVING COUNT(pm.request_id) > p.target_size;
INV-2 시간이 겹치는 중복 배정 문제 2 · M3

한 사람이 시간이 겹치는 두 파티에 동시에 속하지 않는다. 이 질의가 성립하려면 모든 파티에 end_at이 있어야 한다 — 즉시 매칭에 예상 플레이시간을 받는 이유(C1)가 이것이다. 제약을 애플리케이션에 둘지 DB에 둘지는 M3에서 결정한다. DB에 둘 경우 배제 제약은 한 테이블 안에서만 성립하므로 사용자와 시간 구간을 한 행에 모은 user_busy_interval이 따로 필요하다. user_id는 party_member에, 시각은 party에 있어 두 테이블에 걸친 제약은 만들 수 없다.

검사 질의 
SELECT a.user_id, a.party_id, b.party_id
FROM party_member a
JOIN party_member b
  ON a.user_id = b.user_id
 AND a.party_id < b.party_id
JOIN party pa ON pa.id = a.party_id
JOIN party pb ON pb.id = b.party_id
WHERE pa.status IN ('CONFIRMED', 'RECRUITING')
  AND pb.status IN ('CONFIRMED', 'RECRUITING')
  AND tstzrange(pa.start_at, pa.end_at)
   && tstzrange(pb.start_at, pb.end_at);

-- DB로 강제할 경우 — 전용 테이블이 필요하다
CREATE TABLE user_busy_interval (
  user_id  BIGINT    NOT NULL,
  during   TSTZRANGE NOT NULL,
  party_id BIGINT    NOT NULL,
  EXCLUDE USING gist (user_id WITH =, during WITH &&)
);
INV-3 요청 단일 배정 문제 3 · M4

하나의 요청은 최대 하나의 파티에만 속한다. 유니크 제약으로 강제하면 배치가 구조적으로 멱등해진다 — 재실행이 같은 요청을 다시 넣으려 하면 삽입이 실패하고, 그 실패를 정상 흐름으로 처리하면 된다. 락이 아니라 쓰기 자체가 멱등성을 보장한다. 단, 제안 단계에서는 행을 만들지 않는다. 제안 실패 후 재대기(E1~E5)하면 두 번째 행이 생겨 제약에 걸리기 때문이다.

검사 질의와 제약 
SELECT request_id, COUNT(*) AS assigned_count
FROM party_member
GROUP BY request_id
HAVING COUNT(*) > 1;

ALTER TABLE party_member
  ADD CONSTRAINT uq_member_request UNIQUE (request_id);
INV-4 포지션 중복 문제 7 · M6

한 파티 안에서 두 사람이 같은 포지션을 맡지 않는다. 5인 파티는 탑·정글·미드·바텀·서포터를 각각 한 명씩 채운다. 이탈한 자리는 다시 열려야 하므로 부분 유니크 인덱스로 강제한다. 빈자리 모집이 포지션 단위 좌석인 이유가 이것이다 — 좌석 하나가 곧 이 인덱스의 키 하나이고, 동시 지원자 중 하나만 삽입에 성공한다.

검사 질의와 제약 
SELECT party_id, position, COUNT(*) AS dup
FROM party_member
WHERE left_at IS NULL
GROUP BY party_id, position
HAVING COUNT(*) > 1;

CREATE UNIQUE INDEX uq_member_position
  ON party_member (party_id, position) WHERE left_at IS NULL;
INV-5 알림 중복 발송 문제 5 · M5

같은 알림을 두 번 보내지 않는다. 취소된 파티에 알림이 남아 있는 경우도 함께 검사한다. 전송은 at-least-once로 두고 중복 차단은 큐가 아니라 기록 쪽에서 보장한다.

검사 질의 
SELECT dedup_key, COUNT(*) AS sent
FROM notification_job
WHERE status = 'SENT'
GROUP BY dedup_key
HAVING COUNT(*) > 1;

SELECT n.id
FROM notification_job n
JOIN party p ON p.id = n.party_id
WHERE p.status = 'CANCELLED'
  AND n.status = 'SCHEDULED';

데이터 모델

테이블 열여섯 개. 목록이 목적은 아니다. 앞 문서의 불변식 다섯이 스키마의 어느 제약으로 박히는지 보이는 것이 이 문서의 일이다.

권위 있는 상태만 그린다. 여기 있는 것은 전부 PostgreSQL이다. Redis에 있는 것은 마지막 절에 따로 적었다 — 날아가도 불변식이 유지돼야 하는 쪽이라 표에 넣지 않았다.

선은 소유 방향이다. app_user는 거의 모든 테이블에서 user_id로 참조되므로, 선을 다 그리면 그래프가 읽히지 않는다. 그 참조는 아래 엔터티 사전에 적었다.

색이 채워진 넷 — 중복이 DB 제약으로 막히는 테이블이다. 코드가 실수해도, 배치가 두 번 돌아도, 큐가 같은 메시지를 두 번 줘도 데이터베이스가 거절한다.

Redis가 통째로 날아가도 다섯 불변식은 유지된다. 제약이 PostgreSQL에 있기 때문이다. 그래서 아래 다섯은 테이블을 만들지 않았다. notification-events와 discord-commands 큐도 마찬가지다 — 큐는 전달 수단이지 상태가 아니며, 두 큐 모두 at-least-once라 중복 소비는 받는 쪽 테이블의 유니크 제약이 막는다.

제안 전파Pub/Sub인스턴스 간 팬아웃. 상태가 아니라 신호다

실패 조합 억제문자열 + TTL 10분영구 보관하지 않으므로 테이블로 두지 않는다

아직 정하지 않은 것

인덱스 설계 — 결정적 FCFS의 정렬키 (requested_at, id)와 후보 필터 조건의 복합 인덱스는 부하를 재며 정한다.

M0 A1·A2 / I1·I2·I3 "위반을 셀 수 있다" — 도메인 모델·상태 기계·부하 발생기·검출기. 여기서 INV 질의가 먼저 돌아야 이후 단계의 수치가 의미를 갖는다
M1 F1·F3·F4·F5 (무제어) "정원 초과가 눈앞에서 발생한다" — 제어 없는 빈자리 충원으로 INV-1 재현. 부하는 예약 파티로 짜야 한다 — 즉시 매칭 파티는 모집 창이 짧아 경합 밀도가 낮다. 재현 실패 시 부하 동시성과 인스턴스 수를 먼저 의심한다
M2 D6 / F5 재구현 "정원 초과 0, 세 전략의 대가를 안다" — 비관적 락 · 낙관적 락 · 파티션 단일 라이터를 같은 부하로 비교
M3 C1·C5 / D1·D2 / F6 "시간이 겹치는 두 파티에 못 들어간다" — INV-2 차단. 제약 위치(DB 배제 제약 vs 애플리케이션)를 측정으로 결정
M4 C2 / D3 / H1~H4 "배치를 두 번 돌려도 결과가 같다" — 결정적 FCFS + 조건부 쓰기. 락 만료 중 작업 지속까지 포함
M5 C4 / E1~E5 / G1~G4 / H5 "두 인스턴스에 흩어진 참가자가 같은 순간에 제안을 받는다" — 팬아웃·만료·재연결 복구와 알림 회수·중복 차단
M6 B3~B6 / D4·D5 / I4·I5 / E6·F7·G5 "호출을 줄이고, 5인 포지션을 배정하고, 요청 1건의 경로를 복원한다" — 캐싱·병합·스탬피드, 이분 매칭, MDC 추적
M1이 실패 신호를 주면

"위반이 안 나온다"는 좋은 소식이 아니다. 인스턴스가 실제로 2대인지, 부하 발생기가 정말 동시에 지원을 보내는지, 좌석 확정 경로가 우연히 직렬화되고 있지는 않은지를 먼저 확인한다. 재현 건수 자체를 M1의 통과 조건으로 둔다.

부하 프로파일과 입력 분포

씨드 ≠ 타당성

씨드값은 재현성을 보장하지 타당성을 보장하지 않는다. 티어를 균등분포로 뿌리면 성립률이 실제보다 높게 나오고, 실제 분포를 쓰면 크게 달라진다. 입력 분포를 함께 고정한다.

  • 균등 분포 — 알고리즘 자체의 성능을 보는 조건
  • 실제 분포 근사 — 하위·중위 티어에 몰린 실제 롤 분포. 성립률의 현실성을 보는 조건
  • 포지션 선호도 비균등으로 둔다. 서포터·정글 지원이 적은 실제 경향을 반영한다.
